# Mandatory login + policy consent + splash-before-login (Task 1/2, commit 3ee304b)

## Status: WORKING (web + iOS), fast Playwright suite stabilized in 8cbaa78

## What changed
- No guest/anonymous browsing of any screen — Home, Event, Account, disputes, etc. all require a session. A guest visitor lands on the mandatory Login screen instead.
- Login/sign-up requires ticking an unchecked "Tôi đồng ý với Điều khoản sử dụng và Thông báo quyền riêng tư" consent checkbox before submit is allowed.
- Consent is recorded once per account: `profiles.policy_accepted_at` (timestamptz) + `profiles.policy_version` (text).
- Splash now always shows (~2.6s) on cold launch/reopen, including for returning users — previously skipped straight to Home for anyone with saved preferences. Shows before Login *and* before iOS's FaceID lock prompt.

## Fixed: iOS swipe-back gesture (2026-09-16)
Two bugs in the custom edge-swipe gesture (`apps/ios/BanbeApp/Views/RootView.swift` — this app has no `NavigationStack`/`UINavigationController` anywhere; `RootView`'s `ZStack` screen switch reimplements swipe-to-back from scratch with a plain `DragGesture`, so none of the UIKit-specific mechanisms named in the ticket — `interactivePopGestureRecognizer`, its delegate, `navigationBarBackButtonHidden` — literally exist in this codebase; the fixes below are the SwiftUI-equivalent root causes).

1. **Swipe-back worked on Login/Signup** (they're the same `Screen.login` case — Signup is LoginView's own local `mode` state, not a separate screen). `AppState.swift:800-812` `canSwipeBack` excluded `.splash/.langPick/.themePick/.home` but not `.login`, so `goBack()`'s `.login` case (`screen = authBackScreen`) could fire from a swipe even when `authMandatory` was set (the mandatory-login gate that already hides the Back *link* for exactly this reason — nowhere legitimate to go). Fixed by adding `.login` to `canSwipeBack`'s excluded set.

2. **Elsewhere, swipe-back needed a slow, near-full-width drag.** The gesture was attached via `.simultaneousGesture(edgeSwipe)` on the entire `RootView` `ZStack` (`RootView.swift`, previously ~line 168) — meaning it arbitrated against every screen's own `ScrollView` for *every* touch on screen, not just edge-originating ones. A normal-speed partial swipe regularly lost that arbitration to the ScrollView's pan recognizer; only a slow drag (or one persisting nearly the full screen width) reliably got through. Fixed by confining the gesture's hit-testing region to a thin (`edgeSwipeZoneWidth = 20pt`) leading-edge strip (a `Color.clear` overlay, `RootView.swift:131-135`) carrying `.highPriorityGesture(edgeSwipe)` instead — a touch starting outside that strip is never routed to this recognizer at all, so there's nothing left to arbitrate against a ScrollView further in. `highPriorityGesture` (not exclusive/`.gesture`) so a plain tap on something that happens to graze the strip (e.g. a back-button link near the edge) still passes through normally, since it only "wins" once the drag actually recognizes (past `minimumDistance: 4`).

**Verification**: both Debug and Release `xcodebuild` builds clean. Attempted an automated XCUITest (`swipeRight()` and a manual `press→dragTo`) to regression-test fix #1 — discovered XCUITest's synthetic swipe/drag gestures do **not** reliably trigger this custom `DragGesture`-based recognizer at all (the test passed identically whether `.login` was excluded or not, i.e. it wasn't actually exercising the code path either way) — removed that test rather than keep one that can't fail. Confirmation is code-level (traced both fixes against the actual gesture-recognition logic + `canSwipeBack`) plus manual-test steps below, not an automated proof.

## Fix pass (2026-09-30) — splash must complete one animation cycle before FaceID/app entry

Bug: FaceID/app entry could fire before the logomotion animation visibly finished, and the animation itself rendered with blank space/cropping instead of filling its viewport.

### Geometry (why there was blank space)
Root cause, confirmed by reading `public/logomotion/logomotion2309.html`'s own `init()`/`handleComplete()`: the call `AdobeAn.makeResponsive(false, 'both', false, 1, [...])` passed `isResp = false` — the FIRST argument, which is the master on/off switch for the entire scaling branch inside `resizeCanvas()` (`logomotion2309.js`). With it `false`, the function still ran (wiring the `resize` listener) but the computed scale ratio was hard-coded to `1` forever — the stage rendered at its full native authored size (1288x800) inside the real ~280x174 host view the whole time, with `overflow:hidden` silently cropping everything outside the top-left corner. Compounding factor: the file had no `<meta name="viewport">` tag at all, which can make a WKWebView/mobile browser fall back to a legacy ~980px virtual viewport for `window.innerWidth`, further breaking any fit-to-viewport math that assumes real CSS pixel dimensions.
**Fix**: flipped `isResp`/`isScale` to `true` (kept `respDim: 'both'`, `scaleType: 1` = "contain"/`Math.min` fit, matching the export's own 1.61 aspect ratio against the host view's matching 280x174 = 1.609 aspect — same aspect by construction, `SplashView.logomotionAspect` / `Splash.jsx`'s `LOGOMOTION_HEIGHT`, so the fit is a near-exact match, not just "shrink to fit with letterboxing"). Added the missing viewport meta tag. Added `body { display:flex; align-items:center; justify-content:center }` (+ `position:relative` on `#animation_container`, so the pre-existing absolutely-positioned `#dom_overlay_container` still nests correctly under a non-static parent) so any small leftover margin from an aspect mismatch is split evenly instead of pinned to the previous top-left default.

### Completion signal (why FaceID could fire early)
`exportRoot`'s timeline defaults to `loop = true` (`if (loop == null) { loop = true; }`, `logomotion2309.js`) — it was built to loop forever, so there was never a natural "finished" event to hook; the pre-existing `postMessage({type:"logomotion-ready"})` fires on ASSET LOAD (the CreateJS loader's "complete" event), not on animation completion — confirmed these are different points in time by reading the code, not assumed.
**fps = 24** (`lib.properties.fps`), total frame count read at runtime via `exportRoot.totalFrames` (never hardcoded/guessed) — matches `lib.Stage.prototype.getDuration()`/`getTimelinePosition()` (`logomotion2309.js`), which this fix reuses conceptually rather than re-deriving the same math a second way. Actual real-world duration in ms/seconds could not be observed without a browser in this session — the code deliberately reads it at runtime instead of a guessed constant.
**Fix — completion bridge**:
- `public/logomotion/logomotion2309.html` — a second `createjs.Ticker` "tick" listener (`watchForCompletion`, added alongside the existing `stage` listener in `fnStartAnimation`) fires `notifyMotionComplete()` once, the first tick where `exportRoot.currentFrame >= exportRoot.totalFrames - 1`, then removes both Ticker listeners to hold on that final frame (not loop a second time while the host is still waiting on session/bootstrap). `notifyMotionComplete()` posts `{type:"logomotion-complete"}` to BOTH `window.parent` (web) and `window.webkit.messageHandlers.logomotionBridge` (iOS), guarded so it only ever fires once. Reduce Motion (`matchMedia('(prefers-reduced-motion: reduce)')`) skips starting the ticker entirely — renders one static frame (`stage.update()` once) and fires completion immediately.
- Web (`src/screens/Splash.jsx`) — a `message` listener validated against `event.source === iframeRef.current.contentWindow` (never a bare type/origin check alone), calling a new `notifyLogomotionComplete()` action (`GocContext.jsx`) that sets `logomotionComplete: true`. Cleaned up on unmount.
- Web (`GocContext.jsx`) — the pre-existing flat 2.6s `setTimeout` auto-advance is now a bounded FALLBACK only, bumped to 6s (past the animation's real expected duration) so a broken iframe load can't strand the user; a new effect watching `s.logomotionComplete` fires the same advance immediately once the real signal arrives (normally well before the fallback). `postAuthDestination`'s own pre-existing `!sessionChecked` handling (see this file's earlier section) is untouched — this fix only adds the animation-completion gate on top of it, since web's session race was already handled.
- iOS (`Views/LogomotionView.swift`) — added a `WKScriptMessageHandler` `Coordinator` (mirrors `DocumentWebView.Coordinator`'s existing NSObject-subclass pattern in `DocumentViews.swift`), registered for message name `"logomotionBridge"` via `WKWebViewConfiguration.userContentController`, matching the new JS-side `postMessage` call. Surfaces completion via an `onComplete: (() -> Void)?` closure passed into `LogomotionView`. Removed in `dismantleUIView` (`removeScriptMessageHandler(forName:)`) to avoid retaining the coordinator/closure past the view's lifetime.
- iOS (`ViewModels/AuthViewModel.swift`) — added `@Published var sessionChecked = false`, set true once the first `authStateChanges` event of any kind has been processed. iOS had NO equivalent of web's `sessionChecked` before this fix — `SplashView`'s old fixed 2.6s sleep could call `dismissSplash(isSignedIn:)` before the cold-launch session restore ever arrived, misreading an actually-signed-in account as signed out. Mirrors web's `GocContext.jsx` `sessionChecked` exactly (same rationale as `postAuthDestination(prev)`'s own `!prev.sessionChecked` handling, this file's earlier section).
- iOS (`Views/OnboardingViews.swift`'s `SplashView`) — automatic advance now requires `(reduceMotion || animationComplete || fallbackFired) && auth.sessionChecked` (`readyToAdvance`); `fallbackFired` is a bounded 6s `Task.sleep` fallback, same reasoning as web's bumped timer. **Gating decision**: tap-to-dismiss (`advance(force: true)`) is NOT gated on any of this — an explicit user action, matching this app's existing "an impatient tap skips the whole splash" product behavior; only the AUTOMATIC path (and, through it, the FaceID lock prompt gated on `app.screen != .splash` in `RootView.swift`, untouched by this fix) waits for real completion + bootstrap readiness. FaceID's own cancel/retry/failure handling itself was not touched — only the timing of when `dismissSplash` (and therefore the FaceID gate) is allowed to fire.
- Cold-launch-only, confirmed unaffected: `AppState.init()` sets `screen = .splash` exactly once; nothing else ever reassigns `.splash`, so returning from background never remounts `SplashView` or replays the animation — this fix didn't need to add any `scenePhase` handling.

## Fix pass (2026-09-30, second) — hold the completed launch motion for one extra second

Ask: once the animation genuinely finishes, keep showing it for a further 1.0s before advancing to FaceID/login/home, instead of transitioning the instant completion fires.

**Implementation, both platforms — a single named dwell, started at the real completion signal, not at mount/asset-ready/bootstrap-done:**
- iOS (`Views/OnboardingViews.swift`'s `SplashView`): `animationComplete`'s `onChange` now starts a cancellable `Task.sleep(dwellDuration: 1s)` (`startDwellTimer()`) the moment it flips true, ONLY on the non-Reduce-Motion path. `readyToAdvance` becomes `(reduceMotion || fallbackFired || dwellElapsed) && auth.sessionChecked` — Reduce Motion and the bounded load-failure fallback both still count as "ready" immediately (no artificial wait forced onto an accessibility path or an already-broken load); real completion now additionally needs the 1s dwell to have elapsed. Whichever of {dwell, session-ready} finishes later still gates the actual transition — no double-counted delay if bootstrap is already slower than 1s. The dwell `Task` is cancelled on `.onDisappear` and inside `advance(force:)` once a transition actually happens, so there's no stray timer left running.
- Web (`src/state/GocContext.jsx`): the `logomotionComplete` effect now checks `prefers-reduced-motion` itself (native `matchMedia`, not only the iframe's own signal) — Reduce Motion still calls `splashAdvance()` immediately, unchanged; the normal path instead arms a `setTimeout(..., 1000)` (`splashDwellTimer`), and a companion effect watches `s.sessionChecked` so that if bootstrap finishes AFTER the dwell has already elapsed, it advances right away without waiting a second dwell. A `sessionCheckedRef` mirror avoids the dwell's own (necessarily later-firing) timeout callback closing over a stale `sessionChecked` value. Both timers are cleared in `dismissSplash` and on unmount.
- The completed frame does not need any special handling to stay visible during the extra second — the prior fix pass already made the animation hold on its final frame (Ticker listeners removed on completion), so the dwell is simply "wait longer before calling `splashAdvance`/`advance`," not a new rendering state.
- **Tap-to-dismiss decision (unchanged from the prior pass, re-confirmed here)**: `advance(force: true)` (iOS)/the existing tap handler (web) still bypasses the dwell entirely — an explicit user tap remains this product's one deliberate "skip the whole splash" escape hatch; only the AUTOMATIC path (and, through it, FaceID) waits for completion + dwell + session-readiness.
- Not touched: the bounded failure-fallback timeout itself, foreground/resume behavior (cold-launch-only splash mount is unchanged, so this can't replay on resume), FaceID's own cancel/retry/failure logic, `Loading.jsx`/`RootView`'s reservation-hold GIF (unrelated).
