# Map + list explore screen (2026-09-16)

## Status: WORKING (web + iOS), first pass

## Audit findings

**`public.events` already has usable coordinates**: `lat float8, lng float8` (`supabase/migrations/20260906000001_001_core_schema.sql:72-73`), alongside `cat_key`/`cat_label`/`area`/`status`/`visibility`/`seats_remaining`/`starts_at`. Real rows exist for every demo event (`supabase/migrations/20260910000020_020_seed_demo_events_for_test_accounts.sql`), plus any organizer-created event via the real Create Event flow.

**No map anywhere in the app before this** — grepped for `mapkit`/`mapbox`/`maplibre`/`MKMapView`/`leaflet`/`googlemaps` across `src/` and `apps/ios/`: zero hits. `apps/ios/BanbeApp/Services/LocationService.swift` exists but is a one-shot `CLLocationManager` wrapper only ever used to fill in a distance-from-you string on the feed/event-detail screens (mirrors web's `requestFreshCoords()`/`s.userCoords`/`s.located` in `GocContext.jsx:1901-1914`) — reused here, not replaced, for the compass button's underlying location fetch.

**Important architectural fact that changes this screen's data source**: the Home feed the rest of the app shows is driven entirely by a **static, in-memory** catalogue (`src/data/events.js`'s `EVENTS`, built from a hardcoded `ROWS` array) — not a live query. Every event there already carries a `lat`/`lng` (`areaCoords(area) + seededJitter(key)`, `events.js:117-140,192-197`), a `catKey` (matching `FILTER_DEFS` in `src/screens/Home.jsx:7-13` — reused as-is for this screen's category bar, no new taxonomy invented), and a `km` placeholder distance. The 020 migration above turns each of these same event keys into a **real** `public.events` row too (comment there: "so the client can join real assignment data back onto the frontend's rich cosmetic fields... which have no equivalent columns here and are intentionally not duplicated into the database"). This screen queries the **real table** (for live `seats_remaining`/`status`/pagination/bbox filtering — the whole point of the "real-time-ish" requirement) and joins each row's cosmetic fields (photo, description, price display) back from the static catalogue via `findEvent(row.id)`, falling back to a plain rendering using only the DB row's own columns for a real user-created event that has no static-catalogue counterpart at all.

**Category/filter model reused as-is**: `FILTER_DEFS` (`src/screens/Home.jsx:7-13`) — `all`/`supper`/`fashion`/`gallery`/`music`. No icon set exists anywhere for these (grepped `theme.js`/`Home.jsx`/`events.js` for `icon`/`emoji`/`glyph` — zero hits), so the ticket's "matching this app's existing category icon set if one exists" has nothing to match; picked plain, minimal glyphs (SF Symbols on iOS: `fork.knife`/`tshirt`/`paintpalette`/`music.note`; simple inline monochrome shapes on web) rather than inventing a new illustrated icon language the rest of the app doesn't have.

**Disabled-button opacity token, confirmed reused (not invented)**: `apps/ios/BanbeApp/Views/Components.swift:151` (`InkButton`) — `enabled ? app.palette.ink : app.palette.ink.opacity(0.16)`. Web's own disabled-submit convention (`src/screens/Login.jsx`'s `loginBtnStyle`) uses the identical value, `rgba(27,25,22,0.16)`. **0.16 is the one cross-platform "disabled" opacity value this app already has** — used for the dimmed compass button on both platforms.

**Poll cadence reused**: `src/state/GocContext.jsx:667`'s `setInterval(poll, 5000)` (the toast/notification poll, note 07) is the established general-purpose freshness interval — reused for this screen's list/pin refresh, rather than inventing a new cadence.

## Map stack — confirmed free, no billing risk

- **iOS**: native `MapKit` (SwiftUI `Map` + custom `Annotation` views) — no third-party dependency, no key, no usage cap of any kind; it's a system framework.
- **Web**: `maplibre-gl` (npm, MIT-licensed — the library itself is always free regardless of tile source) + **OpenFreeMap** as the tile/style source. Confirmed live and requiring no key/credit card by actually curling it from this session (not just recalled): `curl -sSI https://tiles.openfreemap.org/styles/positron` → `HTTP/2 200`, `access-control-allow-origin: *`, served via Cloudflare cache, no auth header of any kind accepted or required. OpenFreeMap's entire stated purpose is zero-cost, unlimited-usage MapLibre style+tile hosting (PMTiles-based, funded independently of per-request billing) — there is no metering to exceed. Picked the `positron` style specifically (light, minimal basemap) as the closest existing OpenFreeMap style to this app's warm-paper/ink aesthetic; `liberty` and `bright` are the other two published styles, also confirmed live (200).

## Bottom sheet — component chosen per platform

- **iOS**: native `.sheet(isPresented:) { ... }.presentationDetents([.height(peek), .medium, .large]).presentationDragIndicator(.visible)` (iOS 16+; this project's deployment target is iOS 17, `project.yml:4-5`) — gives drag-to-resize, a native grabber handle, and smooth follow-finger snapping entirely for free. No custom gesture code needed here, unlike the web side.
- **Web**: no existing bottom-sheet component or library in this codebase (confirmed via the same grep sweep as the map search) and no new dependency pulled in for it — built a small custom draggable sheet (`src/screens/MapExplore.jsx`'s `BottomSheet`) using pointer events + a CSS `transform: translateY()`, the same "live-follow-finger, no implicit animation mid-drag, snap on release" approach this session already used for iOS's custom edge-swipe gesture (note 09's swipe-back fix) — translated to the web/pointer-event equivalent rather than a new pattern.

## New facts found while implementing

- **`public.events` RLS already scopes to `status = 'live'` for anon/authenticated** (`001_core_schema.sql:122-125`) — the map's real-DB query just adds `.eq('status', 'live')` explicitly (redundant with RLS but makes the client-side intent explicit) rather than needing any new policy.
- **`FILTER_DEFS` exported from `Home.jsx`** (was module-private) so `MapExplore.jsx` reuses the exact same array instead of a duplicate taxonomy — per the ticket's "don't duplicate a separate taxonomy" instruction.
- **New context actions, not new context state**: `goMapExplore`/`backFromMapExplore` (`GocContext.jsx`, next to `goHome`) are the only two additions to the shared context — everything else the screen needs (sheet snap position, category/sort filters, map viewport, loaded events) is local `useState` inside `MapExplore.jsx` itself, since none of it needs to survive leaving the screen or be read by any other screen. `s.userCoords`/`s.located`/`allowLocation()` (already in context, from the existing location-sheet feature) are reused as-is rather than duplicated.
- **iOS mirrors the same split**: `AppState.mapEvents`/`mapEventsLoading`/`locationAuthStatus` are the only new `@Published` state (needed because `AppState` is the one place that owns the Supabase client and `LocationService`); sheet detent and filter state are plain `@State` inside `MapExploreView`.
- **`LocationService` extended, not replaced**: added `authorizationStatus` (read), `isPermanentlyDenied`, `onAuthorizationChange` callback, and a static `openSettings()` — the existing one-shot `request()`/`onUpdate` flow used by the feed's distance strings is untouched and still used by the compass button for the actual location fetch.
- **New model**: `MapEventRow` (`Models/Event.swift`) — a narrower projection of `events` carrying `cat_key` (which the existing `Event` model doesn't have any use for elsewhere, so wasn't added there).
- **Supabase-swift gotcha**: `.gte`/`.lte` are only available on `PostgrestFilterBuilder` (pre-`.order()`/`.limit()`); calling them after `.order()`/`.limit()` (which return `PostgrestTransformBuilder`) fails to compile with "value of type 'PostgrestTransformBuilder' has no member 'gte'". Fixed by building the filter chain first, applying `.order()`/`.limit()` last, right before `.execute()`.
- **SwiftUI persistent bottom sheet**: no first-class API exists for "a bottom sheet permanently up over full-screen content" pre-iOS 26, so `MapExploreView` uses the standard `.sheet(isPresented:)` API with `isPresented: .constant(true)` + `.interactiveDismissDisabled()` + `.presentationBackgroundInteraction(.enabled)` (so the map underneath still receives pan/zoom while the sheet is up) — a known trick, not a new pattern invented here.
- **Compass recenter is still user-tap-only even across a fresh permission grant**: the compass button can trigger `allowLocation()` (which starts the OS prompt), and once `userCoords` lands afterward the map recenters immediately without a second tap — but only because the tap itself set a one-shot `awaitingRecenterAfterGrant` flag first. A background poll/coords refresh alone never moves the map; the compass tap is still the only path that can.
- **Verification performed**: `npx vite build --mode production` (web) — clean, `maplibre-gl` code-splits into its own ~477KB chunk via the dynamic `import()`, not bundled into the main entry. `tests/density-hotspot.spec.js` (new, 4 cases covering empty/null input, single point, densest-cluster-over-outlier, and stable tie-breaking) — all pass. Fast Playwright suite (`--grep-invert "real backend"`) — 275/276 passed; the one webkit failure (`auth-notifications.spec.js`, a different test each run) reproduces identically on the pre-existing `main` branch under parallel workers and passes clean with `--workers=1`, confirming it's pre-existing webkit worker flakiness, not a regression from this change. iOS: both Debug and Release `xcodebuild -sdk iphonesimulator` builds succeed after `xcodegen generate` (new file `MapExploreView.swift` needed re-generating `BanbeApp.xcodeproj`).

## Follow-up fixes (2026-09-16): always-visible map strip, iOS thumbnail, web blank map

**UX restructure**: the map was already architecturally "always visible" (a full-screen `mapDivRef` div sits behind everything; the sheet only visually overlays part of it, so a strip is always uncovered above the sheet — `tall`=0.30 leaves 70% for the sheet/30% map, `peek`=0.86 leaves 86% map/14% sheet, neither ever fully covers the other). What was missing was an explicit, always-present control — previously the three snap points (`tall`/`mid`/`peek`) were reachable only by dragging the handle. Added two buttons directly below the drag handle in `src/screens/MapExplore.jsx` (`data-testid="map-sheet-list-large"` / `"map-sheet-list-small"`) that jump straight to `tall` ("List lớn" — today's default, list large/map small strip) and `peek` ("List nhỏ" — list small/map large, the state that used to be reachable only by dragging all the way down) respectively. The drag gesture itself is untouched and still works as an additional way to move between all three snap points, `mid` included. No iOS change needed here — `.presentationDetents` already exposes its snap points as both a drag gesture *and* is trivially bindable to buttons, but the ticket's two-explicit-buttons requirement was written against the web build's drag-only sheet specifically (iOS's native sheet already lets you tap the grabber area or drag; adding redundant buttons there wasn't asked for and would duplicate what `.presentationDetents` already gives for free).

**Bug 1 (iOS list thumbnail missing) — root cause**: `MapExploreView.swift`'s list row never had an image element at all — just `name`/`area` text. Every other event card in the app draws its photo via `CatalogPhoto(path:height:width:cornerRadius:)` (`Components.swift:6-37`, which wraps `RemoteImage`/`PhotoLoader`), but the map screen's own `MapEventRow` (a live-DB projection, `Models/Event.swift`) has no `img` field to draw from — the web build solves the same gap by joining the DB row back onto the static catalogue via `findEvent(row.id)` (`MapExplore.jsx`'s `fetchLiveEvents`). iOS needed the equivalent join, which didn't exist. **Fix**: `MapExploreView.swift`'s list row now does `EventCatalog.find(ev.id)?.img` and renders it through `CatalogPhoto(path:, height: 52, width: 52, cornerRadius: 10)` — the exact same component/loader path (`PhotoLoader` memory+disk cache, WebP-first, downsampled decode) every other card in the app already uses, not a new one.

**Bug 2 (web map blank) — root cause, confirmed by actually running the dev server under Playwright and reading the console, not guessed**: `maplibre-gl` 6.x ships pure named ESM exports with **no `default` export** (confirmed directly: `Object.keys(await import('maplibre-gl'))` lists `Map`, `Marker`, `NavigationControl`, etc. at the top level; `.default` is `undefined`). `MapExplore.jsx` did `const maplibregl = (await import('maplibre-gl')).default` — `maplibregl` was `undefined`, so `new maplibregl.Map(...)` threw `Cannot read properties of undefined (reading 'Map')` inside an async IIFE with no visible error surface, leaving the map container permanently blank (confirmed via `page.on('pageerror', ...)` in a throwaway Playwright script). The container-height theory from the original ticket (bounding box measured `1280×720` — never zero) turned out not to be the cause here. **Fix 1**: both dynamic-import call sites in `MapExplore.jsx` now use the module namespace directly (`const maplibregl = await import('maplibre-gl')`) instead of `.default`.

**A second, compounding cause surfaced once the above was fixed**: with a real `maplibregl.Map` constructed, the canvas and attribution control appeared but the basemap itself stayed visually blank — `page.on('requestfailed', ...)` showed `.../node_modules/.vite/deps/maplibre-gl-worker.mjs net::ERR_FAILED`. MapLibre loads its vector-tile-decoding work in a Web Worker via its own relative `new Worker(new URL(...))`; Vite's dev-server dependency pre-bundling rewrites/relocates that import, and the rewritten worker URL 404s at runtime — the map style, sprite and tile-source *metadata* all still load fine (so `tiles.openfreemap.org` requests looked completely healthy), but no vector tile ever got decoded into pixels, so the map area rendered as blank paper color forever. **Fix 2**: `vite.config.js` now excludes `maplibre-gl` from dependency pre-bundling (`optimizeDeps: { exclude: ['maplibre-gl'] }`), which stops Vite from touching its worker file. Confirmed fixed end-to-end: after `rm -rf node_modules/.vite` (to drop the stale pre-bundle) and reloading, the same Playwright script showed real `.../planet/13/.../....pbf` tile requests succeeding and a screenshot with actual streets/labels rendered under the pins, not blank. Interesting note for whoever hits this next: `npx vite build --mode production` had "worked" the whole time this bug existed in dev — Rollup's production module interop synthesizes a `.default` even for a module with none, masking the exact bug that broke the dev server. **A clean production build passing is not proof `maplibre-gl`'s import actually works in dev** — this only surfaces by actually opening the dev server in a browser (or Playwright) and checking for a runtime error, not from `vite build` succeeding.

Re-verified after both fixes: fast Playwright suite (`--grep-invert "real backend"`, chromium) — 92/92 passed. `npx vite build --mode production` — still clean. iOS Debug `xcodebuild` — clean.
