- **Web**: `maplibre-gl` (npm, MIT-licensed — the library itself is always free regardless of tile source) + **OpenFreeMap** as the tile/style source. ## Follow-up fixes (2026-09-16): always-visible map strip, iOS thumbnail, web blank map

**UX restructure**: the map was already architecturally "always visible" (a full-screen `mapDivRef` div sits behind everything; the sheet only visually overlays part of it, so a strip is always uncovered above the sheet — `tall`=0.30 leaves 70% for the sheet/30% map, `peek`=0.86 leaves 86% map/14% sheet, neither ever fully covers the other). What was missing was an explicit, always-present control — previously the three snap points (`tall`/`mid`/`peek`) were reachable only by dragging the handle. Added two buttons directly below the drag handle in `src/screens/MapExplore.jsx` (`data-testid="map-sheet-list-large"` / `"map-sheet-list-small"`) that jump straight to `tall` ("List lớn" — today's default, list large/map small strip) and `peek` ("List nhỏ" — list small/map large, the state that used to be reachable only by dragging all the way down) respectively. The drag gesture itself is untouched and still works as an additional way to move between all three snap points, `mid` included. No iOS change needed here — `.presentationDetents` already exposes its snap points as both a drag gesture *and* is trivially bindable to buttons, but the ticket's two-explicit-buttons requirement was written against the web build's drag-only sheet specifically (iOS's native sheet already lets you tap the grabber area or drag; adding redundant buttons there wasn't asked for and would duplicate what `.presentationDetents` already gives for free).

**Bug 1 (iOS list thumbnail missing) — root cause**: `MapExploreView.swift`'s list row never had an image element at all — just `name`/`area` text. Every other event card in the app draws its photo via `CatalogPhoto(path:height:width:cornerRadius:)` (`Components.swift:6-37`, which wraps `RemoteImage`/`PhotoLoader`), but the map screen's own `MapEventRow` (a live-DB projection, `Models/Event.swift`) has no `img` field to draw from — the web build solves the same gap by joining the DB row back onto the static catalogue via `findEvent(row.id)` (`MapExplore.jsx`'s `fetchLiveEvents`). iOS needed the equivalent join, which didn't exist. **Fix**: `MapExploreView.swift`'s list row now does `EventCatalog.find(ev.id)?.img` and renders it through `CatalogPhoto(path:, height: 52, width: 52, cornerRadius: 10)` — the exact same component/loader path (`PhotoLoader` memory+disk cache, WebP-first, downsampled decode) every other card in the app already uses, not a new one.

**Bug 2 (web map blank) — root cause, confirmed by actually running the dev server under Playwright and reading the console, not guessed**: `maplibre-gl` 6.x ships pure named ESM exports with **no `default` export** (confirmed directly: `Object.keys(await import('maplibre-gl'))` lists `Map`, `Marker`, `NavigationControl`, etc. at the top level; `.default` is `undefined`). `MapExplore.jsx` did `const maplibregl = (await import('maplibre-gl')).default` — `maplibregl` was `undefined`, so `new maplibregl.Map(...)` threw `Cannot read properties of undefined (reading 'Map')` inside an async IIFE with no visible error surface, leaving the map container permanently blank (confirmed via `page.on('pageerror', ...)` in a throwaway Playwright script). The container-height theory from the original ticket (bounding box measured `1280×720` — never zero) turned out not to be the cause here. **Fix 1**: both dynamic-import call sites in `MapExplore.jsx` now use the module namespace directly (`const maplibregl = await import('maplibre-gl')`) instead of `.default`.

**A second, compounding cause surfaced once the above was fixed**: with a real `maplibregl.Map` constructed, the canvas and attribution control appeared but the basemap itself stayed visually blank — `page.on('requestfailed', ...)` showed `.../node_modules/.vite/deps/maplibre-gl-worker.mjs net::ERR_FAILED`. MapLibre loads its vector-tile-decoding work in a Web Worker via its own relative `new Worker(new URL(...))`; Vite's dev-server dependency pre-bundling rewrites/relocates that import, and the rewritten worker URL 404s at runtime — the map style, sprite and tile-source *metadata* all still load fine (so `tiles.openfreemap.org` requests looked completely healthy), but no vector tile ever got decoded into pixels, so the map area rendered as blank paper color forever. **Fix 2**: `vite.config.js` now excludes `maplibre-gl` from dependency pre-bundling (`optimizeDeps: { exclude: ['maplibre-gl'] }`), which stops Vite from touching its worker file. Confirmed fixed end-to-end: after `rm -rf node_modules/.vite` (to drop the stale pre-bundle) and reloading, the same Playwright script showed real `.../planet/13/.../....pbf` tile requests succeeding and a screenshot with actual streets/labels rendered under the pins, not blank. Interesting note for whoever hits this next: `npx vite build --mode production` had "worked" the whole time this bug existed in dev — Rollup's production module interop synthesizes a `.default` even for a module with none, masking the exact bug that broke the dev server. **A clean production build passing is not proof `maplibre-gl`'s import actually works in dev** — this only surfaces by actually opening the dev server in a browser (or Playwright) and checking for a runtime error, not from `vite build` succeeding.

Re-verified after both fixes: fast Playwright suite (`--grep-invert "real backend"`, chromium) — 92/92 passed. `npx vite build --mode production` — still clean. iOS Debug `xcodebuild` — clean.

## Follow-up (2026-09-16): iOS "Tìm ở đây" centering bug; in-map pin/list selection + preview card (both platforms)

### Task 1 — iOS "Tìm ở đây" alignment

**Root cause**: `MapExploreView.swift`'s top button row was `HStack { Button(Close); Spacer(); if boundsChanged { Button(SearchHere) }; Spacer(); Button(Compass) }` — SwiftUI splits an `HStack`'s two `Spacer()`s' available width equally, which centers the middle child in whatever space is left over *after* subtracting Close's and Compass's own widths, not the screen's true center. Close ("← Đóng"/"← Close", a text button) and Compass (a fixed 38pt circle) are different widths, so that leftover space was never symmetric — the button sat visibly off toward Compass's side (the narrower neighbor), matching the reported "shifted slightly to the right."

**Fix**: pulled `SearchHere` out of that `HStack` entirely and made it an independent child of the same `ZStack(alignment: .top)` the whole screen is already built on. A ZStack child with no explicit horizontal frame is centered by the ZStack's own alignment (`.top` = center-x, top-y) against the *entire* screen width — independent of Close/Compass's widths, safe-area insets, or sheet state, and with no hardcoded x-offset. `apps/ios/BanbeApp/Views/MapExploreView.swift` (HStack now just Close/Spacer/Compass; the `if boundsChanged { Button(searchHere) }` block moved to its own top-level `ZStack` child, same `.padding(.top, 8)` to keep its prior vertical position).

**Web**: audited, no change needed — `src/screens/MapExplore.jsx`'s search-here button already uses `left: '50%', transform: 'translateX(-50%)'`, which centers it against the full container width directly, entirely decoupled from the back/compass buttons' own (separately, absolutely positioned) placement. There was never an equivalent bug there.

## Follow-up fix (2026-09-16): base map tiles still didn't paint in a production build (only pins showed)

**Checked, in the order asked, before concluding anything**:
1. Container size / `map.resize()` — measured the canvas's real bounding box via Playwright (`page.locator(...).boundingBox()`): always `1280×720`, never zero, in every state (`tall`/`peek`, before/after toggling). `mapDivRef`'s div is `position:absolute; inset:0`, fixed to the full screen regardless of the sheet's snap state — the sheet only visually overlaps part of it, it never resizes the map's own container. So there was never actually a zero/mis-sized-container problem here, and no `map.resize()` call was needed for that reason (ruled out, not guessed).
2. Style JSON — `curl`'d `https://tiles.openfreemap.org/styles/positron` directly again: still resolves, still references `tiles.openfreemap.org/planet` (vector) with no key required. Confirmed **not** the cause.
3. z-index/CSS layering — not the cause either (see below); the canvas element itself was present and correctly sized, it simply never had any pixels painted into it.
4. Console — the actual runtime error was found here, but not as a `console.error`/`pageerror`: reproduced by running `npx vite build && npx vite preview` (a real production build) under Playwright with `page.on('worker', ...)` — **`vite build` had never actually been checked at runtime before this**, only that it compiled — and a worker at `.../maplibre-gl-worker.mjs` (or, after the first attempted fix, a correctly-hashed `.../assets/maplibre-gl-worker-<hash>.mjs`) was created and then **immediately closed**, without ever surfacing as a page error.

**Root cause**: maplibre-gl computes its worker's URL at runtime as `new URL(\`./${t}\`, import.meta.url)` where `t` is a *variable* (`"maplibre-gl-worker.mjs"` chosen conditionally, not a static string literal) — Vite/Rollup's special `new Worker(new URL(...))` bundling detection only fires for a literal string, so it never recognizes or bundles this worker at all. A production build therefore never emits a file at that path; the URL 404s (masked as an HTTP 200 of `index.html` by `vite preview`'s SPA fallback, which the browser then fails to parse as a JS module, silently tearing the worker down). The style/sprite/source *metadata* all still load fine over plain `fetch` from the main thread — that's what made `curl`-testing the style URL and watching network responses look completely healthy — but with no live worker, no vector tile is ever decoded into pixels, so only the DOM-based markers (unrelated to the WebGL canvas) show up. This is dev-vs-prod-only: `vite dev` never hashes/relocates output files the way a build does, so it never exhibited this — the earlier fix in commit 9fa218e (excluding `maplibre-gl` from `optimizeDeps`) was correct for the dev-only worker bug it targeted, but never touched this separate, production-only one.

**First attempt (kept, but not sufficient alone)**: `import('maplibre-gl/dist/maplibre-gl-worker.mjs?url')` + `maplibregl.setWorkerUrl(...)` — makes Vite emit the worker file as a real, correctly-hashed build asset instead of a broken guessed path. This got the worker *created*, but it still closed immediately: the raw worker file itself does `import ... from './maplibre-gl-shared.mjs'`, and a bare `?url` copy is verbatim/opaque — it doesn't bundle or even look at the file's own imports, so once alone in a hashed `assets/` directory, that relative import 404s inside the worker too.

**Actual fix — `vite.config.js`'s new `maplibreWorkerFiles()` plugin**: copies `maplibre-gl-worker.mjs` **and** its sibling `maplibre-gl-shared.mjs` from `node_modules/maplibre-gl/dist/` verbatim (unhashed, original relative names preserved) to a fixed path — a dev-server middleware (`configureServer`) serving them at `/maplibre-gl-worker/*` in dev, and a `closeBundle` copy into `dist/maplibre-gl-worker/` for a production build — so both files sit next to each other exactly as the worker's own relative import expects, in both modes, without special-casing `MapExplore.jsx` per environment. `src/screens/MapExplore.jsx` now just calls `maplibregl.setWorkerUrl('/maplibre-gl-worker/maplibre-gl-worker.mjs')` unconditionally before constructing the map.

**Verified**: `npx vite build && npx vite preview --port 5173` (so Playwright's `reuseExistingServer` picks up the production build instead of the dev server) under a fresh Playwright run — `page.on('worker', ...)` shows the worker created and staying alive (previously: created then instantly closed); the resulting screenshot shows real streets/labels rendered under the pins, not a blank/gray strip. Re-ran with the normal dev server too (`--grep-invert "real backend"`, chromium) — 92/92 still pass, so the dev-mode fix from commit 9fa218e is untouched/still working.

### Bug 2 — Map Explore lost its camera/sheet/filters/selection on return from Event Detail

### Bug 3 — the list couldn't scroll at the mid detent

**Root cause (web) — confirmed by instrumenting, not guessed**: `src/screens/MapExplore.jsx`'s sheet container div had `touchAction: 'none'` on the *whole sheet*, not just the drag handle. Touch-action's effective/"used" value for a touch is the intersection of the touched element's own value and every ancestor's — an ancestor declaring `none` disables native touch scrolling for descendants too, including the list further down, regardless of the list's own (default) touch-action. The drag/scroll *pointer handlers* were already correctly scoped to just the handle (never attached to the sheet or the list) — only the CSS was too broad. **Fix**: moved `touchAction: 'none'` off the sheet container and onto just the handle `<div data-testid="map-sheet-handle">`.

**A second, unrelated, more severe bug found on web while testing the fix above**: `onHandlePointerDown` called `sheetRef.current?.setPointerCapture(e.pointerId)` — capturing the pointer on the *sheet's own outer container ref*, not the handle the listener was actually attached to. Per the Pointer Events spec, once a pointer is captured, subsequent `pointermove`/`pointerup` events retarget to the capturing element and bubble from there — since the sheet container is an *ancestor* of the handle (not the handle itself, and not a descendant either), the handle's own `onPointerMove`/`onPointerUp` could never receive those retargeted events at all. Confirmed directly: a real, slow, stepped drag (`page.mouse.move` in 20px increments with waits between each) never moved the sheet's `top` by even one pixel, in *any* attempt — the drag was fully non-functional before this fix, not merely "conflicting with scroll" as the ticket described (the ticket's own repro was on iOS, which uses `.presentationDetents` and never touches this code path at all — this bug was web-only and pre-existing, just never previously exercised by an automated test). **Fixed**: capture on `e.currentTarget` (the handle itself) instead of `sheetRef.current`.

**Root cause (iOS) — could not be directly confirmed from this sandbox (no simulator UI interaction available)**: `.presentationDetents` + a `List` are documented to cooperate automatically (dragging resizes the sheet; scrolling scrolls the list, with the system switching between the two based on scroll position) — but this project's specific combination of three custom fractional detents, `.presentationBackgroundInteraction(.enabled)`, and `.interactiveDismissDisabled()` is exactly the kind of non-default configuration known to sometimes break that automatic cooperation, which matches the user's own manual repro. **Fix, per the ticket's explicit instruction to use "a handle-only gesture / gesture mask"**: `MapExploreView.swift` — `.presentationDragIndicator(.hidden)` turns off the system's own drag affordance, replaced with a custom `dragHandle` view (a small capsule, `DragGesture(minimumDistance: 2)` attached *only* to that view, snapping `sheetDetent` to the nearest of the three known fractions on release) placed as the first child of `sheetContent`. The `List` itself carries no gesture of any kind, so a touch beginning in its actual rows is never competed for. **Not verified against a real device/simulator** — flagged explicitly in the manual checklist below, since the underlying system sheet-resize gesture recognizer (installed by UIKit, not something SwiftUI code can remove outright) still technically exists alongside this new handle gesture, and only a real interaction test can confirm it no longer wins the arbitration at the mid detent the way it apparently did before.

## Follow-up (2026-09-16): three more UX bugs found on iOS — handle-vs-list arbitration, wrong/janky back-to-map, stale card image

Manual iOS testing after the previous pass (above) found the mid-detent scroll/handle fix was still incomplete, the back-from-Event-Detail control both mislabeled itself and looked janky, and the preview card could show a stale image after a detail round trip. Root causes and fixes below; `MapExploreState` persistence and the two-state card anchor from the previous two passes are untouched.

### Bug 1 — handle vs. list/filter drag arbitration still wrong at MID

**Root cause**: `.presentationDragIndicator(.hidden)` (added in the prior pass) only hides the system's *drawn* grabber — the system's own resize-vs-scroll gesture recognizer is still attached to the whole sheet content view regardless (it isn't something SwiftUI code can remove, only re-bias via `.presentationContentInteraction(_:)`, which this project had never set — it was left at its default, `.automatic`). Two independent, compounding symptoms of that default followed directly:
- A drag starting in the List or the filter row could still be claimed by the system's own resize gesture instead of the List's/ScrollView's own scroll, because `.automatic` arbitration doesn't strictly prefer content scrolling the way `.scrolls` does.
- The custom `dragHandle` (from the prior pass, a `DragGesture` via plain `.gesture(...)`) sat on that exact same non-scrollable strip the system recognizer also considers "resize" territory — a plain `.gesture` doesn't reliably out-prioritize a system-installed recognizer on the identical hit region, which is a plausible explanation for "dragging the handle doesn't move the sheet at all" (the two gestures competing to a standstill rather than either cleanly winning).

**Fix** (`apps/ios/BanbeApp/Views/MapExploreView.swift`):
- Added `.presentationContentInteraction(.scrolls)` to the `.sheet` modifier chain (alongside `.presentationDetents`/`.presentationDragIndicator(.hidden)`/`.presentationBackgroundInteraction(.enabled)`/`.interactiveDismissDisabled()`) — the documented, standard way to tell a `.sheet` + `List` combination "content always scrolls; only resize from a genuinely non-scrollable drag" (the same pattern behind Apple's own Maps app bottom sheet).
- `dragHandle`: `.gesture(...)` → `.highPriorityGesture(...)`, still scoped to only the small capsule view (never the sheet or the List — the ticket's "don't attach a high-priority/simultaneous gesture across the whole sheet or list" is about scope, and this doesn't widen that scope, only strengthens priority within the same small region) — guarantees the custom gesture wins outright on the one region it's attached to.
- Hit region enlarged from ~24pt tall (`4pt capsule + 10pt padding × 2`) to a fixed `minHeight: 40, maxHeight: 40`, full sheet width — within the ticket's specified 36–44pt band, generous without reaching into the filter row directly below it.
- **Not verified against a real device/simulator** — flagged again in the checklist below. `.presentationContentInteraction` is real, documented, public API (not guessed), but this project's specific combination of three custom fractional detents + `.presentationBackgroundInteraction(.enabled)` + `.interactiveDismissDisabled()` is exactly the kind of non-default configuration that made this arbitration behave unexpectedly in the first place, so only an actual interaction test can confirm the system recognizer no longer wins at mid.

**Web audit — no change needed**: `src/screens/MapExplore.jsx`'s handle-drag pointer handlers (`onHandlePointerDown`/`Move`/`Up`) were already, and remain, attached only to the small handle `<div data-testid="map-sheet-handle">` — never the sheet container or the list — confirmed again by inspection and by a new Playwright test (below) that drags from inside the filter row and asserts the sheet doesn't move. There is no system-installed competing recognizer on web the way there is on iOS (this is fully custom pointer-event code), so the web build never had this specific failure mode.

### Bug 2 — back-from-map-event control mislabeled and janky

**Root cause (label, both platforms) — confirmed by reading the actual navigation logic, not guessed**: `goEvent(id)`/`AppState.goEvent(_:)` already correctly set `eventBackScreen = 'mapExplore'`/`.mapExplore` when Event Detail is opened from the map's preview card (neither is `.event`/`.organizer`, so the "remember where we came from" branch fires normally), and `backFromEvent()` already correctly navigated back there. ### Bug 3 — stale preview-card image after a detail round trip

**Root cause — confirmed by reading `RemoteImage`'s actual state logic (`apps/ios/BanbeApp/Views/Components.swift:83-112`), not guessed**: `RemoteImage.task(id: path)` already re-runs when `path` changes (SwiftUI's own per-value task-restart), so on its own that part was fine. The bug is the guard immediately inside it: `guard image == nil else { return }`. `RemoteImage`'s `@State private var image` persists across a `path` change on the SAME view instance (only `init` — which set the state's *initial* value from the memory cache — runs once; a later prop change does not re-run `init` or reset `@State`). Since `selectedCard(_:)`'s call site (`if let ev = selectedEvent { ... selectedCard(ev) ... }`) never gave that subtree an identity keyed to `ev.id`, selecting A then B kept the exact same `selectedCard`/`CatalogPhoto`/`RemoteImage` instance: `path` changed to B's image path, `.task(id: path)` fired again, but `image` was still non-nil (A's already-loaded image) — so the guard returned immediately without even checking B's path, and A's image kept showing under B's now-correct title/meta/CTA.
- **Fix**: `apps/ios/BanbeApp/Views/MapExploreView.swift` — added `.id(ev.id)` to the `selectedCard(ev)` call itself. This forces SwiftUI to treat every selection change as a brand-new view subtree (not a prop update to the existing one): `RemoteImage`'s `@State` is discarded and reinitialized from `init` (which correctly checks the memory cache for the NEW path), and any in-flight load for the previous path is cancelled outright by SwiftUI tearing that old view down — correct even for a rapid A → B → C, since only the final id's subtree survives to apply its own load result.
- **`RemoteImage` itself was deliberately left unfixed** — the same guard bug plausibly exists anywhere else in the app that reuses a `CatalogPhoto`/`RemoteImage` instance's identity across a changing `path` prop, but every other current call site already gets a fresh identity for free (list rows inside a `List`/`ForEach` are already keyed by their own event id), so there was no second confirmed instance of this bug to fix, and widening the change to `RemoteImage` itself (e.g. resetting `image` in an `.onChange(of: path)`) is a real fix but a broader-blast-radius one across every photo in the app, made without any way to test it on-device this pass — noted here for whoever touches `RemoteImage` next, not silently fixed in the same breath.
- **Web audit — no change needed**: `src/screens/MapExplore.jsx`'s card renders `selectedEvent.img` directly as a CSS `background-image` from plain React state on every render — there is no independent async-loading component with its own persisted state to go stale; the browser's own image loading is orthogonal to React's re-render, and the JSX always reflects whichever `selectedEvent` is current. Confirmed by a new Playwright test (below) that does the same A → detail → back → B round trip and asserts the card's title element updated, rather than asserting anything image-specific (there being no failure mode to catch there).

## Follow-up (2026-09-16): edge-swipe vs button parity, top-controls overlap, return-through-poll survival

Reported via manual iOS testing (IMG_6270/IMG_6271) as still-incomplete after the prior two passes. `MapExploreState` persistence and the two-state preview-card anchor are unchanged in spirit — only the "upper" anchor's *value* changed (see Bug 3 below), not its two-state structure.

### Bug 1 — edge-swipe back not equivalent to the "‹ Bản đồ" button

**What was already correct, confirmed by reading, not assumed**: `AppState.swift`'s `backFromEvent()` (called directly by `EventDetailView`'s back pill) and `goBack()`'s `.event` case (called by `RootView`'s edge-swipe commit, `RootView.swift`'s `.onChange(of: isCommittingBack)`) both already funnel through the exact same `backFromEvent()` → `returnToMapExplore()` path from the prior pass — there was never a second, divergent "how do I get back to the map" implementation to reconcile between the two triggers.

**Root cause — confirmed by reading `RootView.swift`'s peek mechanism, then verified by reasoning through the actual timeline, not guessed**: during an edge-swipe drag, `RootView.swift`'s `isPeeking` block renders `screenView(for: app.backTargetScreen)` as a live, non-interactive backdrop UNDERNEATH the dragging Event Detail screen — and when the back target is Map Explore, that backdrop used to be a **full, real `MapExploreView(restored:)` instance**, including its own `.task` (which `await`s `app.loadMapEvents()` and then, on completion, **clears `app.mapExploreState`**). This ran for *every* edge-swipe drag the user started — even ones that never committed (a short drag that springs back to Event Detail) — as a second, independent instance racing whichever instance the *actual* navigation later creates for the one-shot snapshot. A user who so much as touched-and-released near the edge, then later tapped "‹ Bản đồ", could already have had their snapshot silently wiped by this throwaway preview's own `.task` before the real return ever ran — producing exactly "fails to return correctly / partially transitions / broken-reloaded state," and doing so specifically (and only) via the swipe path, since a plain button tap never renders this backdrop at all.

**Fix**: `apps/ios/BanbeApp/Views/MapExploreView.swift` — `init(restored:isPreview:)` gained a new `isPreview: Bool = false` parameter; `.task` now returns immediately (`guard !isPreview else { return }`) before touching `app.loadMapEvents()`/`app.mapExploreState`, and the 5s poll (`onReceive(Timer...)`) does the same. `apps/ios/BanbeApp/Views/RootView.swift` — `screenView(for:isPreview:)` gained the same parameter (default `false`, so every other call site/screen is unaffected); the `isPeeking` backdrop call site now passes `isPreview: true`. The backdrop still renders correctly (it reads whatever `app.mapEvents`/`app.mapExploreState` already hold, which is enough for a static, `.allowsHitTesting(false)` preview) — it just never loads data or mutates shared state.

### Bug 2 — returning from Event Detail still reloads/resets Map Explore

This bug's *reported* symptom is the direct downstream effect of Bug 1's root cause above (a competing, premature `app.mapExploreState = nil`), on both platforms' edge-swipe-equivalent concerns — but a SEPARATE, previously-undiscovered issue surfaced while writing a dedicated Playwright test for "the first post-return polling cycle does not reset map state" (added per this ticket's own testing instructions), on **web**, independent of anything swipe-related (web has no edge-swipe gesture at all):

**Root cause (web pin visually "un-selecting" itself after the first poll after a restore, confirmed via direct instrumentation — a temporary console.log of the poll's returned ids/selectedId, and of the marker-redraw effect's own selectedId, both showed the selection was NEVER actually cleared in React state; only the pin's rendered CSS transform reverted to identity) — `node_modules/maplibre-gl/src/ui/marker.ts`'s `Marker.addTo()` calls `this._update()` synchronously, and `_update()` unconditionally does `this._element.style.transform = <translate-only string>` — i.e. MapLibre's own Marker **always** overwrites the *entire* inline `transform` of whatever element you hand it, discarding anything else already set there. `src/screens/MapExplore.jsx`'s marker code set `transform: scale(1.15)` directly on that SAME element (`el`) MapLibre owns. On the very FIRST selection this was invisible: the `gocPinPop` CSS *animation* (added right after, with `fill-mode: both`) took over the computed `transform` value for that element from then on, silently masking the fact that the underlying inline style had already been clobbered. But every poll tick **removes and recreates every marker from scratch** (`markersRef.current.forEach(m => m.remove())`), and the guard that skips re-triggering the pop animation for a pin that's *already* selected (`lastAnimatedPinIdRef.current !== ev.id`, intentional — "never replayed by a poll refresh while the same pin stays selected") meant the brand-new marker element for a still-selected pin got **no animation at all** — with nothing left to mask MapLibre's own transform overwrite, the selected pin visibly, silently reverted to its unselected scale after the very first poll following any selection (a real, general, pre-existing bug affecting ANY poll while ANY pin is selected — not specific to the restore path, just first exposed by a test written for it).
- **Fix**: `src/screens/MapExplore.jsx`'s marker-drawing effect — the scale/border/shadow/animation styling now lives on an **inner** child div (`pinEl`) appended into a plain, transform-free outer `el`; only `el` (never `pinEl`) is handed to `new maplibregl.Marker({element: el})`, so MapLibre is free to fully own `el`'s own transform forever without ever touching `pinEl`'s. `data-testid="map-pin-<id>"` and the click handler moved onto `pinEl` (the visually/functionally "real" pin), so no existing test needed to change its own selector.

**Root cause (both platforms, the actual "restored state gets discarded" mechanism this ticket describes) — same as the prior pass, reconfirmed**: `MapExploreView`'s/`MapExplore`'s local state is seeded once, correctly, from the snapshot (iOS: `init(restored:)`; web: lazy `useState(() => restored?.field ?? default)`), and neither platform's initial-load effect nor its poll effect ever re-applies density-hotspot centering or resets filters/detent/selection once seeded that way — reconfirmed by the new tests below (which explicitly wait through one full `POLL_MS` cycle post-restore and assert every field is unchanged) rather than re-asserted from memory.

### Bug 3 — selected-event preview card overlaps top controls

**Root cause, both platforms**: the card's "upper" anchor (tall/mid) was a **fixed fraction of the screen/viewport height** (iOS: `cardAnchorFraction` = 0.72; web: `SHEET_SNAPS.tall` = 0.30) — on some device sizes / dynamic-type settings, that fixed fraction placed the card's own top edge ABOVE the close/compass/"Tìm ở đây" row entirely, exactly the overlap in the screenshot. This was never actually validated against the controls' own real position — it was a guessed constant that happened to clear them on whatever size it was last checked against.

**Fix — measured geometry, not a hardcoded offset, on both platforms**:
- iOS (`apps/ios/BanbeApp/Views/MapExploreView.swift`): new `MapTopControlsBottomYKey`/`MapCardHeightKey` `PreferenceKey`s, fed by `.background(GeometryReader{...})` on the close/compass `HStack`, the conditional "Tìm ở đây" button, and `selectedCard(_:)` itself, all read in a shared `"mapExploreTop"` named coordinate space (so all three report positions in the same frame of reference the card is placed in). `topControlsBottomY`/`cardMeasuredHeight` `@State` are updated via `.onPreferenceChange`. The card stays a SINGLE view (bottom-anchored, unchanged shape) so the required smooth cross-fade between "upper" and "peek" keeps working via one `.animation(value: cardBottomPadding)` — only `cardBottomPadding`'s *formula* changed: peek is untouched (`screenHeight * 0.12`, nowhere near the top controls); "upper" is now `screenHeight - (topControlsBottomY + cardTopGap) - cardMeasuredHeight`, i.e. derived directly from the controls' and the card's own actual rendered sizes, never a screen-fraction guess. `cardTopGap` (12pt) is the one remaining literal — deliberately so, since "no gap at all" would look wrong on any device; the overlap-avoiding part of the calculation is fully measured.
- Web (`src/screens/MapExplore.jsx`): the same idea via refs + `ResizeObserver` instead of `PreferenceKey` — `backRef`/`compassRef`/`searchHereRef` (on the three floating controls) feed `topControlsBottom` (`Math.max` of their `getBoundingClientRect().bottom`, re-measured on resize and whenever "Tìm ở đây" appears/disappears); `cardRef` feeds `cardHeight`. `cardBottomPx` replaces the old `cardBottomVh`: peek is `viewportHeight * (1 - SHEET_SNAPS.peek) + 10` (unchanged value, just expressed in px instead of vh so the CSS `transition` interpolates one consistent unit throughout); "upper" is `viewportHeight - topControlsBottom - CARD_TOP_GAP - cardHeight - 8`.
- Camera padding (both platforms) — unchanged from the prior pass (already accounts for the sheet's live fraction + a card-height allowance); the top-controls measurement here only repositions the CARD, not the camera's own framing, since the pin-visibility guarantee was already independently satisfied.
- A genuine, caught-by-testing bug in the FIRST version of this fix (web): the "peek" formula was accidentally written as `viewportHeight * SHEET_SNAPS.peek + 10` (should be `1 - SHEET_SNAPS.peek`) — this pushed the card almost to the TOP of the screen at peek instead of near the bottom, caught immediately by the pre-existing "bug 1: card position" Playwright test (which failed with an obviously-wrong negative/inverted Y value) before this was ever committed. Fixed to the correct `(1 - SHEET_SNAPS.peek)`.

### Animation requirement — restore-only spring/bubble

**Both platforms** add a subtle, restore-only overshoot-then-settle layered ON TOP of the sheet's own existing presentation, gated by a value that is written exactly once, only for a genuinely restored instance, and never touched by polling or filter changes:
- iOS: new `restoreBubbleProgress: CGFloat` `@State`, seeded to `0` in `init` only when `restored != nil` (else straight to `1`, so a fresh open never bubbles at all). Applied to the `.sheet`'s content as `.scaleEffect(0.965 + 0.035 * restoreBubbleProgress, anchor: .top)` + `.offset(y: (1 - restoreBubbleProgress) * 18)`. Animated to `1` exactly once, inside `.task`'s `if hadRestoredState` branch, via `withAnimation(.interpolatingSpring(stiffness: 180, damping: 14))` — SwiftUI's own `.sheet` presentation physics can't be overridden directly, so this doesn't replace that motion, only adds a genuine spring (real overshoot, not a fade) on top of it.
- Web: new `bubbleIn` state, seeded to `!!restored` (`true` only for a genuine restore). A one-time double-`requestAnimationFrame` effect flips it back to `false` right after first paint. The sheet's own container gets an extra `transform: bubbleIn ? 'translateY(14px) scale(0.985)' : 'translateY(0) scale(1)'` with `transition: '... , transform 0.42s cubic-bezier(0.34, 1.56, 0.64, 1)'` — that cubic-bezier is a standard "back out" curve (briefly overshoots past 1 before settling), the closest CSS-easing equivalent of iOS's `.interpolatingSpring` for the same restore-only effect. Never replayed by a later filter change or poll tick, since `bubbleIn` is written exactly once per mount.
- Neither platform's fix touches any existing design token, corner radius, blur/glass material, or color — both are pure-motion additions on top of the unchanged visual chrome.
