# Map search matcher + keyword coverage (2026-09-30)

## Status: WORKING (web + iOS). Live-DB backfill applied (migration 110). Read this before touching Map search or `events.keywords` again.

## Bug report
Typing "Supp" in Map search returned FEWER events than clearing the query and tapping the "Supper club" category chip.

## Root cause (confirmed against the live database, project `ukchdgdnwytretvqjjqu`, service-role read via a throwaway scratchpad script — not assumed)
Two independent, separate matchers: the category chip filters by `cat_key === 'supper'` equality directly (`MapExplore.jsx`'s `visibleEvents`/`MapExploreView.swift`'s equivalent); the OLD text search only ever matched `name`/`area`/`keywords` — **never the category label/key at all**. An event's `keywords` array is organizer-entered (or category-derived as a fallback ONLY when left blank at creation, migration 108) — two real live events (`test-6faea2`, `test-ab56f6`, both `cat_key = 'supper'`) had organizer-typed keywords unrelated to their category (`['Bi','Trung']`, `['Hương','Nhung','Trung']` — test-account first-name lists), so "Supp" never matched them even though the chip did. Confirmed with real IDs:
- Chip ("Supper club", `cat_key = supper`): 8 events.
- OLD text search "Supp": 6 events — missing `test-6faea2`, `test-ab56f6`.
- NEW text search "Supp" (after the fix below): 8 events — full parity, confirmed via `matchesSearchQuery`/`SearchMatch.matches` against the same live rows.

A SECOND, separate root cause was found in the same investigation: `GocContext.jsx`'s `createSubmit` (and iOS's identical `AppState+Data.swift` equivalent) let a non-blank organizer-typed `keywords` field **REPLACE** the category-label default entirely, rather than supplement it — this is exactly how `test-6faea2`/`test-ab56f6` lost their category coverage in the first place, and would keep silently recurring for every future event where an organizer types their own keywords, even after the live-DB backfill below.

## Fix
1. **Matcher itself, one shared document per event, both platforms** (`src/lib/search.js` / `apps/ios/BanbeApp/Lib/Search.swift`) — `buildEventSearchDoc`/`buildDoc` folds name, category label + key + a small bilingual alias dictionary (`CATEGORY_SEARCH_ALIASES`/`categoryAliases`, derived from `Home.jsx`'s real `FILTER_DEFS` — never invented categories), area, city, organizer name, description/intro, and `keywords` as a SUPPLEMENT (never a replacement) into one normalized string. Category/name coverage no longer depends on `keywords` being populated at all — this is the structural fix; the live-DB backfill below is defense-in-depth on top of it, not a substitute.
   - Normalization: NFD-decompose + strip combining marks (accents), explicit đ/Đ → d fold, case-fold, whitespace-collapse (`normalizeSearchText`/`SearchMatch.normalize`).
   - Multi-word query: AND across whitespace-separated tokens (this app had no prior documented multi-word rule to preserve — checked before deciding).
   - Substring/prefix match per token against the normalized document (not exact-word) — "supp" matches inside "supper club".
   - Memoized once per fetched event list (`useMemo` keyed on `events`, web) — never recomputed per keystroke on web. iOS recomputes per render like every other filter in that file already does (not a regression — `visibleEvents` was already an O(n) computed property).
   - No race-guard needed: both platforms filter an already-loaded, synchronously-held event list on every keystroke — there is no per-keystroke network round-trip for this search (unlike `GocContext.jsx`'s `createAddressSeq`-style debounced address lookups), so "a slow in-flight request overwriting a newer one" doesn't apply here structurally.
   - RLS/visibility untouched — filtering happens client-side over rows the existing `status = 'live'` query (and RLS) already returned; no new query bypasses anything.
2. **Web select additions** (`MapExplore.jsx`'s `fetchLiveEvents`) — added `cat_label`, `city`, `description`, `intro`, `organizers(name)` to the existing `.select(...)`, and attached `catLabel`/`city`/`organizerName`/`description`/`intro` onto the mapped event object (previously only `cat_key` was attached, `cat_label` was fetched but silently dropped).
3. **iOS model/select additions** — `MapEventRow` (`Models/Event.swift`) gained `catLabel`/`city`/`description`/`intro`/`organizers` (new `MapEventOrganizerJoin: Codable, Hashable` — a dedicated join struct, NOT a reuse of `AppState+Team.swift`'s `EventCreditOrganizerJoin`, which is `Decodable`-only and broke `MapEventRow`'s own `Codable` synthesis). `AppState+Data.swift`'s `loadMapEvents` select mirrors web's addition.
4. **Create/edit-event keyword supplement fix** (both platforms) — `GocContext.jsx`'s `createSubmit` and iOS's `AppState+Data.swift` equivalent now compute `keywords = dedupe(categoryKeywords + organizerKeywords)` (capped 20, matching `set_event_keywords`'s own server-side cap) instead of `organizerKeywords.length ? organizerKeywords : categoryKeywords`. Category coverage can no longer be silently dropped by typing any keywords at all. Both create AND edit/resubmit share this one computed value (confirmed by reading both call sites).

## Live-database backfill (migration `20261022000110_110_backfill_category_keyword_coverage.sql`)
- Idempotent, additive-only SQL: for every event whose `keywords` doesn't already contain its own `cat_label`/`cat_key` (case-insensitive), appends both — never removes/reorders an organizer's existing entries, never touches a row that already has category coverage.
- Audited via a throwaway scratchpad script (`/private/tmp/.../scratchpad/audit_search.mjs`, service-role client) BEFORE writing the migration — snapshot of pre-change rows dumped via the same script (**erratum**: the snapshot file was written before AND after the migration to the same path, and the post-run write overwrote the pre-run one before it was archived separately — the pre-values for the two affected rows were still captured in this session's own terminal transcript and cross-checked, but the JSON snapshot file itself does not preserve the true "before" state; if this needs to be redone cleanly, timestamp the snapshot filename before writing next time).
- Applied for real via `npx supabase db push` against the live project (`ukchdgdnwytretvqjjqu`) — confirmed in `supabase migration list`.
- **Before**: 16 live events total, 0 with genuinely blank `keywords` (migration 108's own `WHERE keywords = '{}'` backfill had already covered every truly-empty row) — but 2 (`test-6faea2`, `test-ab56f6`) had non-empty keywords that didn't include their own category, invisible to migration 108's backfill condition.
- **After**: same 16 rows; only `test-6faea2` (`["Bi","Trung"]` → `["Bi","supper","Supper club","Trung"]`) and `test-ab56f6` (`["Hương","Nhung","Trung"]` → `["Hương","Nhung","supper","Supper club","Trung"]`) were actually changed — the other 14 already had `"Supper club"`/their own category text present. Zero rows skipped due to a blocker; no migration/data-write failure.

## Not done / explicitly out of scope this pass
- Organizer name / description / intro were added to the search document design but MapExplore's own query only fetches `organizers(name)` for the currently-loaded event set — no new join/index was added to the `events`/`organizers` tables themselves (the existing `organizer_id` FK + embed already supports this at no schema cost).
- No new database index was added for text search (`events_keywords_gin_idx` from migration 108 already covers the `keywords` array; the new matcher's category/area/organizer text is small enough, and the working set (`status = 'live'`, currently 16 rows) small enough, that client-side filtering remains the right architecture — same conclusion migration 108's own doc comment reached).
