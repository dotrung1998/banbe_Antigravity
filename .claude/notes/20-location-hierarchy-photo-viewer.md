# Multi-level location selector + event-photo viewer fit/fill (2026-10-24)

## Status: WORKING (web + iOS), schema applied and backfilled on the live project. Read this before touching the area/location picker, Home/Map location filtering, or `PhotoViewer.jsx`/`PhotoViewerView.swift` again.

## A. Location hierarchy — data-driven, not a hand-authored geography database

The old `AreaSheet`/`AreaOption` was a hardcoded 4-bucket Saigon-only list (`q1`/`thaodien`/`binhthanh`/`other` + a disabled `danang` placeholder), matched by plain substring against `events.area` text. Map applied NO location filter at all. Replaced with a hierarchy built entirely from real events' own geocoded location fields — a node exists if and only if a real, currently-eligible event has that location, plus the two country roots (VN/US) which are always shown even with zero events (honest empty state, never a seeded fake event).

**Schema** (migration `20261024000112_112_location_hierarchy_fields.sql`, additive only, applied and confirmed via `supabase migration list` — local/remote both show `20261024000112`): `events.country_code text`, `events.state_province text`, `events.neighborhood text`, all nullable. `area`/`city`/`address_line`/`lat`/`lng` untouched. `create_event_draft`/`resubmit_event_for_review` RPCs gained matching optional trailing params (default NULL, backward compatible with any client not yet updated).

**Backfill** (`scripts/backfill-location-hierarchy.mjs`, idempotent, rate-limited 1.1s/request per Nominatim policy, dry-run by default, `--write` to persist, re-checks `.is('country_code', null)` at write time so a re-run can't clobber a concurrent write): reverse-geocodes each row's OWN existing, already-trusted `lat`/`lng` — never touches `area`/`address_line`/`lat`/`lng` themselves, never invents a value. Run for real against the live project. **Actual before/after**: 30 total rows, all three columns null before; after, 28/30 have `country_code` (`'VN'`), 1/30 has `state_province` (`'Tỉnh Lâm Đồng'`, the Da Lat event — every HCMC-area row has `state_province = null` because Nominatim doesn't return a `state` tag for Ho Chi Minh City, a direct-controlled municipality, not a script bug), 22/30 have `neighborhood`. Skipped: `test-real-event-8334a5`, `test-s-ki-n-8444c8` — both have no `lat`/`lng` at all, logged not fabricated.

**Known cross-platform inconsistency, flagged not silently fixed**: iOS's `AddressSuggestion` derives `stateProvince` from MapKit's `administrativeArea`, which DOES return a value for HCMC (e.g. "Hồ Chí Minh") — unlike Nominatim (web), which returns null for HCMC's `state` tag. This means an iOS-created HCMC event going forward will land at `c:VN|s:Hồ Chí Minh|...` while every existing/web-created HCMC event sits at `c:VN|...` with no state level. Not reconciled this pass (doing so would mean guessing a state for web/backfilled rows, which the ticket explicitly forbade) — worth a follow-up decision (e.g. either accept MapKit's admin-level value as correct and backfill web/Nominatim rows using city-name fallback for known municipalities, or teach iOS to also treat HCMC/Hanoi/Da Nang as state-less to match web).

**Hierarchy shape**: Vietnam/US roots (VN first) → state/province (skipped if absent, e.g. HCMC events sit directly under the country) → legacy/familiar-area group (VN only — the raw `events.area` string, explicitly labeled "khu vực quen thuộc"/"familiar area", never presented as a current official administrative unit, per Vietnam's 2025 removal of district-level government) → neighborhood leaf. US: country → state → city → neighborhood (no `area`/district level — US counties/districts are never invented or mechanically mapped from "quận"). A node with no country code sits under a separate "Chưa rõ quốc gia"/"Country not set" root, shown only when such rows exist — never assumed to be VN.

**Node IDs**: built from raw column values only, never display labels or list position (e.g. `c:VN|a:Quận 1`, `c:VN|s:Tỉnh Lâm Đồng|a:Da Lat`, `c:US|s:California|ci:San Francisco|n:Mission`), `%`/`|` percent-escaped. Counts are the distinct event-ID set under each node (never a sum of child counts — matches `src/lib/badges.js`'s existing "one real array, never re-summed" dedup convention from a prior pass).

**Legacy key migration** (`migrateLegacyAreaKey`/`LocationHierarchy.migrateSelection`, one pure function per platform, unit-tested): `q1`→`c:VN|a:Quận 1`, `thaodien`→`c:VN|a:Thảo Điền`, `binhthanh`→`c:VN|a:Bình Thạnh`, `other`/`danang`→`c:VN` (no single-node equivalent), `all`/empty→`all`, anything already in the new shape passes through unchanged, anything unparseable→`all`. `s.area`/`app.area` was never actually persisted across reloads on either platform (confirmed by grep — no UserDefaults/preferences key for it) — always in-memory, resets to `'all'` on relaunch; kept that way, it just now holds a node ID instead of a legacy key.

**Search**: reuses the existing Map-search normalization (`src/lib/search.js`'s `normalizeSearchText`/`matchesSearchQuery`, `Lib/Search.swift`'s `SearchMatch`) directly rather than reimplementing accent/đ-insensitive matching a third time. Matches reveal their ancestor path and temporarily expand just enough of the tree to show them; clearing search restores the user's own manual expand/collapse state exactly (stored by node ID, never row index).

**Home/Map wiring**: Home's main feed filter and its previously-duplicated weekend-strip district table now both go through the one shared `curArea.match`/`matchesArea` function (web: `Home.jsx`; iOS: `AppState.swift`'s `matchesArea` overloads) — the duplicate table is gone. Map (`MapExplore.jsx`/`MapExploreView.swift`), which previously had zero location filtering, now applies the same filter to its list and pins, with a new location chip opening the shared sheet; the existing GPS/"nearby" permission flow is completely untouched — selecting any location, including the US root, never triggers a location prompt. Neither platform filters the signed-in user's own tickets/bookings by this — only the discovery/browse feed.

**Files**: new `src/lib/locationTree.js`, `apps/ios/BanbeApp/Lib/LocationHierarchy.swift` (pure tree/match/search/migration logic, unit-tested both platforms: `tests/unit/location-tree.test.mjs`, a scratch `swiftc` harness run against the 11 real area strings). ## B. Event-photo viewer — aspect-fit foreground, aspect-fill blurred backdrop

Investigation found no literal solid-black letterbox in the prior code — both platforms already used crop-to-fill (`background-size:cover`/`.scaledToFill()`) for the foreground photo, the OPPOSITE problem: the photo was cropped into a small fixed `33vh`-tall box, with the surrounding ~2/3 of the screen being a very dark blurred backdrop (`brightness(0.62)` + a `rgba(12,12,12,0.28)` dim ≈ 45% brightness) — dark enough to read as "black bars" even though nothing was literally `#000`. `ChatPhotoViewer.jsx`/`ChatPhotoViewerView.swift` (a separate component, chat image attachments) does have genuine solid-`#000` styling but was confirmed unrelated and untouched.

**Fix, both platforms, `PhotoViewer.jsx`/`PhotoViewerView.swift` only** (`StoryViewer`/`PulseViewer`/`ChatPhotoViewer` untouched): foreground is now the full, uncropped photo (`object-fit: contain`/`.scaledToFit()`), sized to the largest box that fits the usable viewport (safe-area- and caption/control-chrome-aware) — replacing the fixed 33vh crop-to-fill box. Backdrop blur/dim values (radius 34, `brightness(0.62)`/`black 0.38`) are unchanged, only now correctly fills 100% of the viewport behind a variably-sized foreground instead of behind a fixed-height box. iOS additionally fixed a real small edge-transparency gap (`.blur(radius:34)` without `opaque` faded the backdrop's own edges to transparent at the 1.24x overscale — changed to `opaque: true`) and now shares one decoded image between foreground and backdrop (matching cache keys) instead of decoding the same photo twice.

Existing custom paging/tap-half-navigation/horizontal-drag-paging/vertical-drag-to-dismiss-with-shrink-to-origin-rect gesture code (no library, both platforms) is unchanged — the dismiss animation reads the photo's live on-screen rect, so it follows the new variable size automatically; only its zero-size guard was hardened (an unloaded `<img>`/image would otherwise report a 0×0 rect and produce an infinite scale on close).

**Fit math verified by hand** for a 390×844 safe-area-aware viewport (available box ≈ 350×651, ratio 0.5376): 9:16 portrait → 350×622 (width-limited); 16:9 landscape → 350×197 (width-limited); 1:1 square → 350×350; 3:1 panorama → 350×117 (width-limited). All sane, no upscaling past native resolution, no distortion.

**Verified this pass**: `vite build` clean (included in the combined build above); iOS build succeeded as part of the same combined `xcodebuild` run. **Not verified**: actual visual rendering on a simulator/device, the existing `tests/navigation-and-events.spec.js` Playwright spec that measures photo-0's box for a swipe gesture (flagged by the implementing pass as worth re-checking if photo aspect ratios differ across a gallery, not run this pass).
