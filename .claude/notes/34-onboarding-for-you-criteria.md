## Decisions worth knowing (read before changing anything)

1. **Preferences are NOT a `profiles` column** (deviation from the brief, deliberate). `profiles_select_for_organizer` (migration 021) lets a host `SELECT` the whole `profiles` row of anyone who booked/messaged them, and Postgres cannot hide a single column from a row policy. A `profiles.event_preferences` column would have handed every host each guest's full answers, contradicting "owner-only, never reveal to hosts". Instead: `public.profile_event_preferences` (RLS on, **no grants** to anon/authenticated) reached only through owner-scoped `SECURITY DEFINER` RPCs (`get_my_event_preferences`, `save_my_event_preferences`, `complete_settings_onboarding`, `complete_preferences_onboarding`). Same validated JSONB (`event_preferences`, CHECK = `validate_event_preferences`), plus separate onboarding markers (`settings_onboarded_version`, `prefs_onboarded_version`) and `preferences_version` (bumps on every save; iOS `eventPrefsVersion` — the For You refresh key). Revoking column privileges on `profiles` instead would break `select *` for every client incl. web, and every future column — rejected.
2. **Who is prompted** = accounts created after the migration's apply time (`event_onboarding_config.cutover_at`, set once by the migration) **or** accounts with `prompt_requested_at` set by the separate test backfill. Existing users get no prompt, no markers, no invented answers — no mass write at all.
3. **Marketing consent** reuses the existing `host_promo_consent` (OFF by default, `consent_version`, `consented_at`/`withdrawn_at`, existing Account > Security unsubscribe). The onboarding toggle goes through the same explicit-confirmation + `set_host_promo_consent`.
4. **Face ID stays device-local**; Face ID/location are persisted enabled only after the real iOS authorization/biometric check succeeds. Continue-without is always available.
5. **Recommendation ≠ eligibility.** `ForYou` (Lib/ForYou.swift) only ranks; `events.reservation_criteria` is the only thing that can block a reservation, and only on interests/goals.

## Data model (migration 162, rollback `supabase/rollbacks/20261210000163_163_revert_event_preferences.sql`)

`event_preferences` v1: `{version:1, interests[], goals[], availability[], budget:{tier,currency?}, languages[]}`. Absent key = skipped; `["no_preference"]` = explicit no preference (exclusive in its array). Ids: interests = existing category ids (`supper,fashion,gallery,music,popup`), goals = `meet_people,learn,experiences,networking`, availability = `weekdays,weekends,daytime,evening`, languages = `vi,en,other`, budget tier = `free,low,medium,flexible,no_preference` with `currency` `VND|USD` required for low/medium/flexible (ambiguous budgets are rejected by the CHECK). Budget ranges (iOS `BudgetRegion`): VN low ≤ 200.000₫, medium 200.001–600.000₫; US low ≤ $25, medium $25.01–$75; free = price 0; flexible = no limit.

`events.reservation_criteria` (default `{"version":1,"mode":"everyone"}`, CHECK = `validate_reservation_criteria`): `{mode:"declared", interests?:{rule:any|all, values[]}, goals?:{…}}`. **ANY** = guest declared at least one value; **ALL** = every value; with both groups present **both** must hold. Only interests/goals from the taxonomy (budget/schedule/language/consent/location/DOB/anything else are rejected by the CHECK). Organizer owner always bypasses.

Enforcement: `assert_reservation_criteria(events)` is `PERFORM`ed in **`hold_seats`** (the live path) and **`claim_seats`** (legacy) after the invite gate and the `events … FOR UPDATE` lock, before the capacity count — so it composes with locking/capacity/payment/invite rules and a concurrent criteria edit cannot interleave. `hold_seats_with_attendees` (151) calls `hold_seats`, so it is covered. Error: `CRITERIA_NOT_MET` with the eligibility JSON in `DETAIL` (exact `missing_interests`/`missing_goals`, `interest_rule`/`goal_rule`). `check_my_reservation_eligibility(event)` is the pre-check for the caller only. `gift_ticket`/`claim_gift_ticket` transfer an already-reserved seat (no new reservation) and are intentionally **not** gated. Existing bookings are never invalidated by a criteria change (verified).

## For You — matching rules (deterministic; `Lib/ForYou.swift`)

Candidates = real discoverable public events only (`discoveryEvents`; the demo catalogue is never recommended), composed with the Home area filter. An event is a match iff all hold:
- bookable (live, not cancelled/ended/sold out/invite-only) and not started yet;
- **Interests (hard when chosen):** a *known* event category outside the chosen set excludes it; unknown category passes; "no preference"/skipped adds nothing. Match +50.
- **Budget (hard cap only when comparable):** `free` tier ⇒ paid events excluded (+20 for free). low/medium cap in the **budget's** currency; the event's currency is VND for VN (and legacy rows with no country) — `events` only stores `price_vnd`. For any other country the event currency is unknown ⇒ budget is **neutral** (no FX rate is ever invented; a USD budget therefore never excludes a VND/unknown-priced event). Within cap +20; free event under a non-free tier +10.
- **Goals (soft):** documented affinity (`meet_people`→supper/popup/music, `learn`→gallery/fashion, `experiences`→all, `networking`→popup/fashion/supper), +10 per matching goal, capped +20.
- **Availability (soft)**, evaluated in the **event's** time zone (VN → Asia/Ho_Chi_Minh; US → by `state_province` code/name; unknown ⇒ not compared): all picked dimensions fit +10; any mismatch −15 (never excludes).
- **Languages:** neutral — events have no language field yet (a host-declared event language would be a separate migration).
- Recency nudge up to +5 inside 14 days; needs at least one affirmative signal besides it. Order: score desc, soonest start, key.
Missing optional data never excludes every event (nil start/zone/price still match on interest). The gold star shows only when ≥1 match exists under the current area filter; it auto-resets if matches vanish; it refreshes when `eventPrefsVersion` changes.

## Onboarding UX
Order after the existing gates (phone/DOB) and under the Face ID lock: **settings review** → **five questions**. Server markers make both once-only (skip counts as done; skipping stores no answers). Defaults-ON (haptics, emailed payment documents) apply to brand-new accounts only; a prompted existing account sees and keeps its current values and only changed toggles are written. Account > Preferences > Event preferences edits the same answers (also opened from the unmet-criteria card with "Save and go back").
