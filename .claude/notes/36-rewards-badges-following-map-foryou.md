Status: IMPLEMENTED LOCALLY (web + iOS + migration 165), NOT applied/deployed/committed. Nothing is live until `supabase db push` applies **165** (and any earlier pending migration, see notes 34/35). Until then the app degrades safely: a missing rewards RPC (`PGRST202`/`42883`) hides the Home streak/coin shortcuts and shows "Rewards aren't available yet" — no placeholder numbers. Design references only (not proof of retention uplift): Meetup-style interest/location matching, Strava-style milestone badges, a streak/rewards shortcut. The coin/badge numbers are an MVP product proposal, not market-derived.

## 1. For You on Map
- One matcher: `src/lib/forYou.js` `forYouCandidateFromEvent` / `forYouRankEvents` / `mapForYouSet` / `applyForYouFilter` (iOS `ForYou.candidate(...)` + `AppState.mapForYouMatches`). Home now builds its candidates through the same function, so the two surfaces cannot score differently. No scoring rule was duplicated or changed.
- Map's candidate pool = the events Map has loaded (so it follows **Search here**/pagination), narrowed by the selected area exactly as Home does, then ranked. The For You set is ANDed onto area/category/open-now/search; pins and list read the same `visibleIdSet`, non-matching geolocated events stay the existing passive dots.
- Toggling the chip never flies the camera, never changes zoom, sheet detent or list scroll (it is deliberately NOT in the `catFilter`/`openNowOnly` effects that snap the sheet). Selected preview card stays independent of filters (existing rule).
- Gold-star chip pinned at the leading edge of the status row; the other chips scroll in their own scroller (`data-hscroll`, root tab swipe ignores it; iOS `HStack` pinned chip + `ScrollView`). Shown only when the account has saved preferences; empty/loading states + "Edit preferences" (row while active, and inside the empty state). Edit preferences saves the map snapshot (`forYou` + `searchQuery` added to it) and returns through `eventPrefsReturnScreen = mapExplore`.
- "New matches" attention is **read + acknowledge only** on Map (`useForYouAlert({passive:true})`, iOS `ForYouAlertModel.attach`): Home owns observation, so a partial viewport can never baseline/flag matches.
- RLS / invite-only / server-side booking criteria untouched (Map query still `visibility='public'`; eligibility is still enforced in `hold_seats`).

## 2. Following
- Canonical, account-scoped state: web `src/lib/followSync.js` (framework-free, unit-tested) mirrored into context (`followedOrgIds`, `followedHosts`, `followedStatus`, `followWriteError`); iOS `AppState+Following.swift` (+ pure `FollowLogic`). Every Follow/Following control (organizer profile, Pulse sheet, public-profile organizer card) goes through one write path (`setFollowing`): optimistic, one write per host, double-tap ignored, failure **reverts and says so**, success re-reads the truth.
- Account switch/sign-out clears the list immediately and a late response or write for the previous account is dropped (uid re-checked after every await). Other devices: web re-reads on foreground (`visibilitychange`, ≥15 s apart); iOS re-reads on sign-in, whenever Account > Following opens, and after every write and `get_organizer_profile`'s server-fresh `following` is folded in.
- Markers: "✓ Following" as **inline text** (never over an avatar → no clash with story rings) on the organizer profile button, the event-detail organizer row, Pulse event cards and the Pulse host sheet. Home story rings are untouched.
- Account > Following (`/profile/following`, iOS `.following`): searchable (name only, accent-insensitive), real name/avatar/verified from `organizers`, row opens `openOrganizerProfile(id)`, Unfollow asks first, empty state, retry on load error, a host that is no longer readable stays listed as "no longer available" with Unfollow only. The list is owner-only (RLS) and never published; follower *counts* elsewhere are unchanged.

## 3. Rewards & badges (migration 165; rollback `supabase/rollbacks/20261212000166_166_revert_rewards.sql`)
**Server-authoritative.** Tables (RLS on, **no client grants**): `reward_rule_versions`, `reward_ledger`, `reward_attendances`, `reward_attendance_sources`, `reward_active_days`, `reward_badge_defs`, `reward_user_badges`, `reward_catalog`, `reward_unlocks`. Client doors (all `authenticated`, owner via `auth.uid()`): `get_my_reward_summary`, `get_my_rewards`, `get_my_unlocked_cosmetics`, `redeem_reward(code)`, `record_active_day('save', eventId)`. Internal `rewards_*` helpers are not executable by clients.
- **Ledger** is append-only (UPDATE/DELETE blocked except the cascade from deleting the account). Unique `(user_id, source_key)` + unique reversal link ⇒ idempotent across devices/retries. A wrong award is undone by a **reversal entry**, never an edit.
- **Rules v1** (`reward_rule_versions`, JSON, one active row; every ledger row stores the version): onboarding +10 once; attendance +20 per **distinct** event; cap = 10 coin-paying events per local month (200 coins), beyond it the award is recorded as 0 (`attendance_cap`) — badges/streak still progress, bookings are never touched. No coins for app opens, spending, likes, follows, repeated saves, uploads, cancellations, consent.
- **Attendance** = a host-confirmed `check_ins` row (trigger `rewards_checkin_*`, plus per-seat `booking_attendees.checked_in_at`). `rewards_sync_booking(booking)` reconciles from live facts, so undo → reversal and re-check-in → one new award key `attend:<event>:<cycle>` (net still +20, verified with 4 cycles). Excluded: the event's owner, any accepted team member, self check-ins (`checked_in_by = attendee`), cancelled events (cancelling later reverses). **Gifts:** the claimed recipient earns; the purchaser who did not attend earns nothing.
- **Onboarding** pays only on the first 0→completed transition **with answers** (skip pays nothing; completing after an earlier skip does not retro-pay; editing never pays again). No back-fill of anyone who finished earlier.
- **Redemption** (`redeem_reward`): per-user advisory lock, balance re-read inside it, unique `redeem:<code>` ⇒ a retry/second device is never double-charged; `INSUFFICIENT_BALANCE` charges nothing. 12 concurrent calls on one account (`13b_concurrent_redeem.sh`) → 1 charge, never negative.
- **Reversal after redemption:** the reversal is always applied in full, so the balance **can go negative**; the unlock is never revoked; nothing is blocked and no penalty exists — redemption just needs earning back to ≥ price.
- **Badges** derive from facts (`reward_attendances`, onboarding entry, ended events) and are re-evaluated on every change; an undone attendance revokes a badge it no longer supports. Ready to explore / First outing (1) / Regular (5) / Explorer (3 distinct `cat_key`) / Community regular (10) / Host milestone (3 `status='ended'` events each with a valid non-owner attendee). Badges are **private**: no visitor read exists, nothing is shown publicly (there is no public-visibility toggle yet by design).
- **Streak** did not exist before this pass (no fire icon/streak anywhere in either codebase), so it is defined here: an *active day* = a server-verified **save** (`favorites.created_at`, stamped by trigger; pre-existing favorites are NULL = not eligible) or a valid attendance. App opens, polls, searches do not count. One row per local date; **fixed zone `Asia/Ho_Chi_Minh`** (UTC+7, no DST) for streak dates and the monthly cap. Alive through yesterday; a missed day resets to 0 with **no** penalty and nothing blocked. Streak never creates coins.
- **Cosmetics:** reuses the existing keychain system. 3 new designs `rwd-comet`/`rwd-lantern`/`rwd-crown` (group `rewards`, manifest `reward:true`, 40/80/120 coins) are locked until redeemed (enforced by `save_my_keychain` → `DESIGN_LOCKED` **and** a table trigger because owner policies allow direct writes). The 24 built-in charms stay free. Web/iOS pickers show a lock → Rewards.
- **Home header:** one glass capsule with two separate buttons (🔥 streak, coin balance), each ≥44 pt, both open Account > Rewards & badges, plus the unchanged Search circle. Narrow phones: the "Home" title drops first, then the wordmark shrinks (iOS `ViewThatFits`; web ResizeObserver + `src/lib/homeHeaderLayout.js`). Edit-answers row is unchanged (shown while For You is active).
- **Backfill:** none automatic. `scripts/rewards-backfill-preview.sql` is a READ ONLY dry run that prints what a legacy backfill *would* grant under the live rules; there is deliberately no apply path.

## Known limitations (report, do not hide)
1. **Unclaimed gifts credit nobody.** A seat checked in before the recipient claims it earns no one, and claiming later does not retro-pay (claim is refused after the event ends anyway).
2. **Multi-ticket bookings:** the system can't tell which seat is the booking holder's, so the holder earns once when the host confirms the first admission from that booking; a seat imported by another account earns that account when that seat is checked in.
3. Multi-account farming is not addressed beyond the existing phone-verification gate.
4. A failure inside reward bookkeeping is caught and logged as a WARNING so it can never block a check-in; the sync is idempotent, so the next check-in/undo/event-end for that booking repairs it (there is no scheduled repair job).
5. The per-attendee check-in path in migration 151 never clears `booking_attendees.checked_in_at` on `undo_check_in` (pre-existing); rewards react to the booking-level `check_ins` delete, which is the real undo.
6. Search is not an active-day source (cannot be verified server-side).
7. Negative balances are possible (see reversal-after-redemption).
