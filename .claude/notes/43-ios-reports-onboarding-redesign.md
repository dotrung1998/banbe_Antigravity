Status: IMPLEMENTED LOCALLY (iOS only), NOT committed/deployed. No migration, no RPC change, no web change. Simulator-verified with DEBUG fixtures only (no real account, no device).

## Reports (Account > Metrics & Reports)
- Still ONE `get_account_kpis` call (migration 097, applied remotely) feeding screen, CSV, JSON, PDF and chart PNG. Auth/organizer-id handling untouched (`openReports`/`fetchAccountKpis` params unchanged).
- Pure mapping in `Lib/ReportsPresentation.swift`: role layout (personal: primary confirmed_bookings; host: primary confirmed_seats; admin: attention FIRST, primary platform_new_bookings), "needs attention" only for NON-ZERO actionable backlogs (personal outstanding_refunds; host refunds_overdue then refunds_owed; admin pending_event_reviews, unresolved_disputes). A flagged metric is not repeated in the overview; "All metrics" lists everything so nothing is unreachable. Unknown future keys still show with the server label.
- Honesty: NO deltas/growth badges anywhere (there is no prior-period query). Point-in-time metrics are never charted. Peak day / active days come only from the returned series and hide when the series has no activity.
- Fixes found: (1) the old on-screen range label used `ISO8601DateFormatter()` without fractional seconds, so real payloads (`…:56.789+00:00`) rendered a BLANK range — now tolerant parsing; (2) series day buckets were parsed in the device TZ (could shift a day) — now UTC calendar days; (3) a quick 7→30→90 switch could land an older response last — `reportsRequestSeq` guard; (4) a failed refresh wiped visible data — now kept, shown as stale with time + Retry.
- Exports moved to the header overflow menu (PDF/JSON) and the metric detail sheet (CSV, Save chart image); the share sheet opens automatically. Export functions are byte-identical — guarded by `ReportsExportGoldenTests` (captured green against the PRE-change code first). Note: the PDF export still uses the fractional-only parser for its range line (left unchanged on purpose to preserve output; a range with exactly .000 ms would print blank there).
- Components: `Views/ReportsDashboardComponents.swift` (card surface = existing `field` fill, 20pt radius, soft light-mode shadow / dark hairline; Swift Charts sparkline + trend chart with VoiceOver summary sentence; attention card = icon + text badge + leading rule, never colour alone; static skeleton with the loaded footprint).

## Onboarding
- Flow: Welcome → Goals → Interests → Availability → Budget → Languages (one per screen, "n of 5", Back, Skip, Continue) → save → reveal → settings (only if owed) → Home with For You on (only if real matches). State machine `Lib/OnboardingFlow.swift` (pure, tested); screens `Views/OnboardingFlowViews.swift`; RootView keeps the overlay up via `onboardingFlowActive` after the server markers clear.
- Server contract UNCHANGED: `complete_preferences_onboarding(p)` (nil = skipped everything, marker only) and `complete_settings_onboarding`. Preferences still owner-only via RPC; nothing moved to `profiles`. Recommendation ≠ eligibility untouched.
- Draft: `OnboardingDraftStore` — device-local UserDefaults `banbe.onboardingDraft.v1.<uid>`, answers + position only, resumed only while the server still owes the step (server wins), cleared on completion and on sign-out.
- Save failure: honest screen with Retry / Edit answers / Skip for now (session-only, as before). Reveal: real `discoveryEvents` + real `ForYou` ranking + Home area filter; loading, offline (`discoveryEventsLoadFailed`, new flag), zero-match (offers "all areas" only when matches exist elsewhere) states. "What your answers change" copy is derived from the matcher's actual rules (languages honestly marked "saved, doesn't filter").
- Settings step trimmed to haptics + emailed documents + promotional texts (own section). Face ID moved to the Home activation checklist (contextual) and Account > Security (unchanged, device-local); location removed — Map/area picker already request it when needed, manual area unchanged.

## DECISION NEEDED (not changed): promotional-texts consent
The settings step pre-sets "Host promotional texts" ON for new accounts and records agreement when the user taps Continue (`set_host_promo_consent(true)`). Wording, default and write are kept EXACTLY as before. A pre-enabled toggle + "Continue = agreement" is likely not explicit opt-in consent (e.g. Vietnam Decree 13/2023: silence/non-response is not consent). Recommended: default OFF (or an explicit Yes/No choice) — a product/legal decision; no DB change needed (consent version/columns already exist). Also pre-existing: when `hostPromoConsent` failed to load (row disabled), Continue still writes the default for a new account.
