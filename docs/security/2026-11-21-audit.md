## 1. Phase status — RAN vs UNAVAILABLE

Skill đầy đủ được thiết kế cho một harness có sub-agent song song và OS
sandbox. Môi trường này chạy được phân tích tĩnh, test local và SQL trên
throwaway stack, nhưng không có independent sub-agent/sandbox như skill mô tả.
Vì vậy **không claim full 6-phase coverage**.

| Phase | Status | Đã làm / lý do không chạy |
|---|---|---|
| 0. Recon | **RAN** | Inventory `api/` routes + rewrites trong `vercel.json`; đọc `api/auth`, `notify`, `payment-webhook`, `payment-document`, `photo-share`, `media`, `wallet`, `calendar`/`geocode`, cron; 224 migrations; prior audit `docs/audits/2026-11-19-cc/APPLIED.md`. |

## 2. Confirmed findings và fixes

Severity là mức của **đường đi đã xác nhận trong code**, không phải CVSS mù.
Các mục `Medium` được giữ lại vì user yêu cầu residual-risk report đủ để
reviewer đọc, không phải để làm report dài.

### H-1 — Admin tự cấp `can_manage_admins` (High)

- **Policy**: `supabase/migrations/20260906000001_001_core_schema.sql:110-111`
  (`profiles_update_own`) chỉ giới hạn **row** `auth.uid() = id`, không giới
  hạn cột.
- **Quyền thực tế**: grant UPDATE mặc định của Supabase cho `authenticated`
  phủ mọi cột, gồm `can_manage_admins` (`20261102000121_121_admin_team_invites.sql:40`).
- **Đường đi**: một admin **không** có `can_manage_admins` gọi
  `PATCH /rest/v1/profiles?id=eq.<self>` với `{"can_manage_admins":true}`.
  Sau đó `public.can_manage_admins()` (`121:44-51`) trả true, nên
  `set_admin_management_permission()` (`121:334-339`) và các RPC quản lý team
  mở cho chính họ. Đây là privilege escalation trong admin team.
- **Fix**: migration mới
  `supabase/migrations/20261231000233_233_server_owned_columns_guard.sql`
  thêm trigger `profiles_guard_client_write` (BEFORE INSERT OR UPDATE) pin
  `role`, `can_manage_admins`, `phone_verified`, `attended_count`,
  `no_show_count`, `referral_code`, `referred_by`, `created_at` cho
  `authenticated`/`anon`; SECURITY DEFINER RPC và service role đi qua owner
  nên vẫn ghi được.
- **Proof**: `supabase/tests/233_server_owned_columns/test_guards.py` check
  `client cannot self-grant admin-team permission`; pass 14/14.

### H-2 — Host tự gắn badge “Đã xác minh” và xoá `disputes_open` (High)

- **Policy**: `001_core_schema.sql:118-119` (`organizers_update_own`) lại chỉ
  check row owner, không check cột.
- **Hiển thị**: `src/screens/OrganizerProfile.jsx:276` render
  `org.verified ? ' · ✓ Đã xác minh'`; `src/screens/AdminEvents.jsx:194` ghi
  chú rằng `verified` “has NO real write path” — thực tế direct PATCH đã mở.
- **Đường đi**: host gọi `PATCH /rest/v1/organizers?id=eq.<own>` với
  `{"verified":true}` (public select policy `001:114-115` cho mọi người đọc),
  hoặc `{"disputes_open":0}` để xoá counter đang được các RPC dispute tăng
  (`026:797`, `042:173`, `138:115`, …).
- **Fix**: cùng migration 233, trigger `organizers_guard_client_write` pin
  `verified`, `disputes_open`; admin/service path vẫn ghi được. Test:
  `client cannot self-award organizer verified/disputes`, pass.
- **Rollback proof**: rollback file khôi phục đúng direct write; test
  `rollback restores organizer self-verification` pass.

### H-3 — Participant sửa `body`/`sender_id` của message người khác (High)

- **Policy**: `supabase/migrations/20260921000064_064_messages_update_read_by_participant.sql:20-22`
  chỉ kiểm tra thread membership; `messages_insert_participant`
  (`003_social_chat.sql:85-98`) cũng chỉ kiểm tra participant.
- **Client thật**: chỉ update `read_at`
  (`src/state/BanBeContext.jsx:9674`).
- **Đường đi**: bất kỳ participant nào gọi
  `PATCH /rest/v1/messages?id=eq.<message-của-người-khác>` với
  `{"body":"..."}` hoặc `{"sender_id":"..."}`; UPDATE grant mặc định phủ mọi
  cột. Trong thread thanh toán/tranh chấp, đây là sửa lời nhắn/“bằng chứng”
  của bên kia.
- **Fix**: migration 233 `REVOKE UPDATE ON public.messages FROM authenticated, anon;`
  rồi `GRANT UPDATE (read_at) ON public.messages TO authenticated;`.
  Không đụng POLICY (vẫn cho participant mark read).
- **Proof**: test `client cannot rewrite another participant message body`
  trả `permission denied`; `client can still mark a message read` trả `ok`.
  Rollback proof: body rewrite lại được — chứng minh chính migration đã đóng.

### H-4 — Direct `profiles` INSERT tự đặt `role='admin'`/`can_manage_admins` (High, defense-in-depth)

- **Policy**: `profiles_insert_own` (`001:108-109`) chỉ check `auth.uid() = id`;
  không có trigger bảo vệ INSERT (trigger `guard_profile_role` chỉ là
  `BEFORE UPDATE OF role`, `016:48-64`).
- **Đường đi**: user chưa có profile (profile bị xoá/trigger signup lỗi) gọi
  `POST /rest/v1/profiles` với `id` của mình, `role='admin'`,
  `can_manage_admins=true`. Bình thường `handle_new_user` đã tạo profile nên
  precondition hẹp, nhưng đây vẫn là một write path không được phép.
- **Fix**: trigger 233 áp dụng cả INSERT: role participant, cờ false, counts 0,
  referral code do server sinh, `referred_by` null, `created_at` now.
- **Proof**: test `client cannot insert a privileged profile row` trả
  `participant|false|false|0|0|...` (referral code server sinh, `referred_by`
  rỗng), pass.

### H-5 — Host-derived origin đi vào password-reset redirect (High, conditional on Host trust)

- **Code**: `api/_lib/authLookup.js:120-129` (`getRedirectUrl`) trước fix đọc
  thẳng `x-forwarded-host`/`host`; `api/auth/index.js:149-155` đưa origin đó
  vào `admin.auth.admin.generateLink({ type: 'recovery', options: { redirectTo }})`.
- **Đường đi**: request reset password với `Host`/`X-Forwarded-Host` do kẻ tấn
  công chọn (nếu platform/proxy không ghi đè) → email recovery có
  `redirect_to` trỏ domain attacker; sau khi Supabase verify, trình duyệt có
  thể bị đưa sang domain đó cùng phiên/token tùy auth flow.
- **Điều kiện chưa chứng minh**: không có quyền probe Vercel trong phiên này,
  nên **không khẳng định** Vercel cho Host tùy ý. Vì vậy severity ghi
  “High nếu Host spoof được”; fix loại bỏ điều kiện đó.
- **Fix**: `api/_lib/origin.js` allowlist host (`banbe.app`,
  `www.banbe.app`, `PUBLIC_SITE_URL`, `VERCEL_URL`/branch/prod host,
  `ORIGIN_ALLOWLIST`, localhost), fallback canonical; `getRedirectUrl` dùng
  `requestOrigin()` (`authLookup.js:129`). Unknown host không bao giờ thành
  origin.
- **Proof**: `tests/unit/security-hardening.test.mjs` 10/10, gồm
  `getRedirectUrl refuses an unallowlisted forwarded host`,
  `requestOrigin never reflects an unknown or malformed Host`.

### H-6 — `payment-document` Host injection vào HTML hóa đơn (Medium, fixed)

- **Code**: `api/payment-document.js:72` trước fix tạo
  `https://${req.headers.host}`; `src/lib/paymentDocument.js:270` chèn thẳng
  `${origin}` vào `src="..."` của `<img>`.
- **Đường đi**: nếu Host chứa `"`/attribute payload, HTML hóa đơn (mang tên,
  địa chỉ, mã số thuế của khách) có thể bị chèn attribute/element; đây là
  stored-ish HTML injection qua request, không cần đăng nhập để trigger nếu
  có token hợp lệ.
- **Fix**: `requestOrigin(req)` (canonical/allowlist) +
  `escapeHtml(origin)` ở `paymentDocument.js:270`. Test
  `renderPaymentDocument escapes the origin used in the wordmark URL` pass.
- **Residual**: token vẫn có thể nằm trong `?token=`; đã có `no-referrer`,
  chưa chuyển sang header-only vì iOS webview cần.

### H-7 — Referral link HTML injection trong email check-in (Medium, fixed)

- **Code**: `api/notify.js:166-172` trước fix đưa `referralLink` thẳng vào
  `<a href="${referralLink}">`; `src` referral code lấy từ
  `profiles.referral_code`.
- **Nguồn**: `profiles.referral_code` direct-writable qua
  `profiles_update_own` (001:110-111) và không có format constraint
  (`023_referrals.sql:15-18`); `referral_code` có thể chứa `"`/HTML.
- **Fix**: encode code (`encodeURIComponent`) + `escapeHtml(referralLink)`
  trước href (`notify.js:166-172`), và migration 233 pin `referral_code`
  (chỉ server sinh/giữ) cho client. `handleWelcome` cũng encode
  (`notify.js:552`); CTA của nó đã được escape từ trước
  (`emailTemplate.js`).
- **Verification**: code path đã đổi tại `notify.js:166-172` (encode trước khi
  ghép URL, escape trước khi vào `href`); DB pin được test ở migration 233.
  Không có harness gửi Gmail thật trong phiên này, nên đây là code-path +
  DB proof, không phải email-delivery test.
- **Residual**: code cũ đã tồn tại trong DB vẫn có thể dị dạng; encode/escape
  ở sink bảo vệ email, và pin ngăn ghi mới.

### H-8 — Direct `social_links` bỏ qua sanitizer (Medium, fixed)

- **Code**: `save_profile`/`update_organizer_profile` sanitize qua
  `sanitize_social_links` (`102:22-65`, `102:100`, `102:157`), nhưng direct
  `profiles_update_own`/`organizers_update_own` (001:110-119) vẫn UPDATE được
  `social_links` mà không đi qua RPC.
- **Impact**: lưu link `javascript:`/`data:`/host giả; React 19 chặn
  `javascript:` href ở client hiện tại, nên không phải stored XSS high, nhưng
  vẫn là link phishing/không đúng platform và làm sai dữ liệu public.
- **Fix**: trigger 233 gọi `sanitize_social_links` khi INSERT hoặc khi cột
  thay đổi; invalid → `INVALID_SOCIAL_LINKS` (check_violation). Test
  `direct invalid profile social link is rejected` và organizer variant pass.

### H-9 — Participant tự tạo message `kind='system'` (Medium, fixed)

- **Policy**: `messages_insert_participant` (`003:85-98`) không giới hạn
  `kind`; client UI render system message như thông báo chính thức.
- **Đường đi**: participant `POST /rest/v1/messages` với `kind='system'`,
  `sender_id=self`, body “Host đã xác nhận thanh toán…”.
- **Fix**: trigger `messages_guard_client_insert` (migration 233) ép
  `kind='text'` cho client; RPC/service role vẫn ghi system message.
- **Proof**: test `client cannot insert a fake system message` trả `text`.

### H-10 — `joi` high advisories qua `passkit-generator` (High dependency, fixed)

- **Trước**: `passkit-generator@3.7.0` pin exact `joi@17.13.4`
  (`node_modules/passkit-generator/package.json`), `npm audit` báo 2 high:
  `joi` (`GHSA-6h2x-m376-mqjq` / CVE-2026-92599, `isoDate()` ReDoS) và
  `passkit-generator` chỉ vì kéo `joi`.
- **Reachability thực tế**:
  - App dùng `pass.setRelevantDate(new Date(ev.starts_at))`
    (`api/_lib/walletPass.js:220`); `passkit` chuyển Date qua
    `Utils.processDate` rồi validate, không nhận raw string của host.
  - App **không** set `contactVenueEmail`, `semantics`, `expirationDate`
    (không có trong `walletPass.js`), nên nhánh
    `email({ multiple: true })` không được gọi từ input người dùng.
  - Tuy vậy, đây là dependency high; deferral không cần thiết vì có fix
    không breaking.
- **Fix**: `package.json:49-50` `"overrides": { "joi": "17.13.9" }`; không
  downgrade `passkit-generator`. `npm ls joi` → `joi@17.13.9 overridden`;
  `node -e "import('passkit-generator')..."` load OK; `npm audit` 0.
- **Không dùng `npm audit fix --force`** (sẽ hạ `passkit-generator` 3.1.2).
